### 1. Part B assumes raw `namefrst_ans` and `namelast_ans` exist alongside `*_ans_cleaned` in `divided_file<yr>` shards

`part-b-raw-ans-variable-existence` · **MAJOR** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/marshall_diag.do:92-98`

**What the code does**  
Lines 92 and 94 execute `use histid [sex] namefrst_ans namelast_ans namefrst_ans_cleaned namelast_ans_cleaned using "\`d'/\`f'", clear`, and line 98 runs `abeclean namefrst_ans namelast_ans, sex(sex) nickname nonysiis`. In `MATCHING/0_create_file_for_matching_intgenV4_women_added.do:85-87`, however, the raw variables merged from `name_only<yr>.dta` are named `namefrst` and `namelast`, and in `MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:150,169-170`, `namefrst_ans` resolved only as a Stata prefix abbreviation for `namefrst_ans_cleaned` when `namefrst_ans_cleaned` was the sole `namefrst_ans*` variable loaded in memory (as documented in `MATCHING/1e_tgtns_divided_files.do:15-18`).

**Why it matters**  
If the `divided_file<yr>[_women_added]` shards contain `namefrst_ans_cleaned` and `namefrst_ans_nysiis` without a separate raw variable literally named `namefrst_ans`, `use ... namefrst_ans ... namefrst_ans_cleaned` will abort with `r(111)` (`namefrst_ans ambiguous abbreviation`), or if only `*_ans_cleaned` is present, fail because the variable is specified twice or missing at line 98 after `rename`.

**Suggested fix**  
Verify with `describe using` whether `namefrst_ans` and `namelast_ans` exist as distinct raw variables in all four `divided_file{1930,1940}{,_women_added}` directories; if the divided files store only `namefrst_ans_cleaned` (and `namefrst_ans_nysiis`), merge raw `namefrst`/`namelast` from `name_only<yr>.dta` or `matching_intgen<yr>[_women_added].dta` by `histid`, or re-clean the stored `namefrst_ans_cleaned`/`namelast_ans_cleaned` (`sf`/`sl`) if testing whether a second `abeclean` 0.26 pass changes the stored cleaned names.

### 2. Part A contracts `f_M f_W` and `l_M l_W` over the union `f_M!=f_W | l_M!=l_W` without filtering each field to differing pairs

`part-a-unfiltered-pair-contract` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/marshall_diag.do:64-74`

**What the code does**  
Line 64 filters to `keep if f_M!=f_W | l_M!=l_W`, and then lines 67 and 71 run `contract f_M f_W` and `contract l_M l_W` directly without first restricting to `keep if f_M!=f_W` and `keep if l_M!=l_W` (unlike Part B at lines 118 and 125).

**Why it matters**  
When first names differ on many records while surnames agree (as in 1940, where 287,379 men have `f_M != f_W` and almost all have `l_M == l_W`), `contract l_M l_W; gsort -_freq; list in 1/\`=min(30,_N)''` at lines 71-73 tabulates identical surname pairs (`l_M == l_W`) among men with a first-name difference, swamping any genuine surname discrepancies in the top-30 list (and similarly for `contract f_M f_W` on records where only the surname differs).

**How to check**  
Compare `MATCHING/marshall_diag.do:64-74` against `MATCHING/marshall_diag.do:116-131`: in Part A, any record with `f_M != f_W` and `l_M == l_W` remains in memory when `contract l_M l_W` runs at line 71.

**Suggested fix**  
Mirror Part B (`MATCHING/marshall_diag.do:117-130`) by filtering each branch to differing records before contracting: inside `preserve`/`restore`, add `keep if f_M!=f_W` and guard `contract f_M f_W` with `if _N`; after `restore`, add `keep if l_M!=l_W` and guard `contract l_M l_W` with `if _N`.
