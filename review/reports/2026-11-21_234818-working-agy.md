### 1. Head-human fill of empty model-ditto surnames is scored against blank rather than the linking pipeline's Ancestry fallback

`head-human-fill-scored-against-blank-instead-of-ancestry-fallback` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/ditto_diag.do:111-114, MATCHING/ditto_diag.do:130-144, MATCHING/ditto_diag.do:180-186, MATCHING/ditto_diag.do:376-379, MATCHING/ditto_diag.do:397-398`

**What the code does**  
On non-target records (`nt`, where `namelast == fs_namelast`), line 185 defines `gen byte nt_diff_pre = nt & !(namefrst_ml==namefrst & namelast_ml_ditto==namelast)` and line 186 defines `gen byte nt_diff_h = nt & !(namefrst_ml==namefrst & namelast_h==namelast)`, while lines 180 and 182 count empty model-ditto surnames with `head_anc == namelast` (`nt_d_fill`) as `Fixed: was wrong or empty, becomes right`. However, in the linking pipeline (`MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:169-170`, noted at lines 136-137), empty `namefrst_ml` and `namelast_ml_ditto` already fall back to the record's own Ancestry name (`namefrst`, `namelast`), which on non-target records is 100% equal to the agreed human name. Likewise, on target records, line 112 (`replace namelast_h = head_anc if de & head_agree`) overwrites empty model-ditto surnames even when the record's own Ancestry and FamilySearch surnames already agree (`tgt_de_own_agree`: `namelast == fs_namelast`).

**Why it matters**  
In the Wyoming smoke test (`MATCHING/results/ditto_diag_SMOKE.md:38-55,80-81,97-99`), this framing makes the head-human fill appear to reduce non-target departures from 11.15% to 10.58% (and fix 1,051 empty non-target ditto surnames) and achieve 87.90% `= both` on target records (`g1`). Relative to the linking pipeline's actual own-record Ancestry fallback, filling empty surnames with `head_anc` fixes 0 non-target records, breaks the 18 empty-surname non-target ditto records in `wy` where `head_agree == 1 & head_anc != namelast` (which `nt_d_break` at line 181 omits because it requires `namelast_ml_ditto == namelast`), and on target records in `wy` produces the exact same surname as the existing Ancestry fallback on 154 of 157 `g1` records (98.1%), matches FamilySearch against Ancestry on 0 records, and overwrites an agreed own-record surname (`namelast == fs_namelast`) with a different head surname (`head_anc != namelast`) on 2 records.

**How to check**  
In MATCHING/ditto_diag.do, define the baseline linking surname with its actual Ancestry fallback (`gen namelast_base = cond(namelast_ml_ditto=="", namelast, namelast_ml_ditto)` and `gen namefrst_base = cond(namefrst_ml=="", namefrst, namefrst_ml)`) and compare `namelast_h` against `namelast_base` on both `tgt` and `nt`. In MATCHING/results/ditto_diag_SMOKE.md (wy), check how many of the 157 `g1` target records and 1,051 `nt_d_fill` non-target records actually change relative to `namelast_base`.

**Suggested fix**  
Score `namelast_h` against the linking pipeline's actual baseline fallback (`cond(namelast_ml_ditto=="", namelast, namelast_ml_ditto)`) rather than against `""`, restrict `replace namelast_h = head_anc if de & head_agree` on target records to cases where the record's own humans disagree on the surname (`namelast != fs_namelast`), and include empty-surname non-target ditto rows where `head_agree & head_anc != namelast` in `nt_d_break` rather than treating empty non-target surnames as departures from the agreed name before the fill.

### 2. Literal "InvalidPred" in `namefrst_ml` and `namelast_ml_ditto` is treated as valid non-empty model output throughout Sections 0-3

`invalidpred-treated-as-nonempty-valid-name` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/ditto_diag.do:77, MATCHING/ditto_diag.do:95, MATCHING/ditto_diag.do:102-114, MATCHING/ditto_diag.do:128-129, MATCHING/ditto_diag.do:148-155, MATCHING/ditto_diag.do:160-165, MATCHING/ditto_diag.do:189-194`

**What the code does**  
Section 4 (`lines 189-194`) counts the literal failure string `"InvalidPred"` in `namefrst_ml`, `namelast_ml`, and `namelast_ml_ditto` (`565`, `19,940`, and `348` records in `wy`, including `139` non-ditto heads where `"InvalidPred"` remained in `namelast_ml_ditto` and propagated down the ditto chain to `209` ditto rows; `MATCHING/results/ditto_diag_SMOKE.md:104-109`). However, Sections 0-3 test only `==""` and `!=""`: line 77 (`gen byte de = d & namelast_ml_ditto==""`), line 95 (`head_le`), line 104 (`de_headcross`), line 110 (`replace namelast_x = head_ld if de & head_nd & head_ld!=""`), lines 128-129 (`g2`, `g3`), lines 148-155 (`fail_pre`, `fail_x`, `fail_h`), and lines 160-165 (`nt_f_e`, `nt_f_w`, `nt_d_l_e`, `nt_d_l_w`, `nt_nd_l_e`, `nt_nd_l_w`) all treat `"InvalidPred"` as a non-empty transcribed name.

**Why it matters**  
Ditto rows whose `namelast_ml_ditto` is `"InvalidPred"` (carried down from the 139 non-ditto heads with `namelast_ml == "InvalidPred"`) are excluded from `de` and never receive the head-human fill `namelast_h`; if a chain headed by `head_ld == "InvalidPred"` crosses an image boundary into an empty ditto row, line 110 copies `"InvalidPred"` into `namelast_x` and counts it as a successful cross-image model fill (`dx = 1`, `fail_x = 0`); and in Sections 1-3 `"InvalidPred"` is scored as a present-and-wrong transcription (`= neither` / `present and wrong`) rather than unusable model output. (In the linking pipeline `MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:119,169-170`, `"InvalidPred"` likewise bypasses the `==""` Ancestry fallback and enters `abeclean` as `"invalidpred"`.)

**How to check**  
In `wy/merged_data.dta`, run `count if tgt & (namefrst_ml=="InvalidPred" | namelast_ml_ditto=="InvalidPred")` and `count if d & namelast_ml_ditto=="InvalidPred" & head_agree` to see how many target and ditto records carry `"InvalidPred"` as if it were a valid transcription.

**Suggested fix**  
Either normalize `"InvalidPred"` to `""` on `namefrst_ml` and `namelast_ml_ditto` (or define `de`, `head_le`, `fail_*`, and the empty indicators in Section 3 to treat `=="InvalidPred"` as empty/unusable alongside `==""`) after or separately from recording the raw `"InvalidPred"` counts in Section 4, and explicitly block `head_ld == "InvalidPred"` from being carried into `namelast_x` at line 110.

### 3. Cross-image chaining assigns the previous image's head to top-of-page `non_ditto_ml==0` rows, and `namelast_x` omits `& head_cross`

`cross-image-chain-assigns-prior-page-head-and-namelast-x-omits-head-cross` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/ditto_diag.do:74, MATCHING/ditto_diag.do:85-94, MATCHING/ditto_diag.do:102-113, MATCHING/ditto_diag.do:179-182`

**What the code does**  
Line 74 links `row == 1` of `image` to `row == 40` of `image - 1` on the same roll, and line 85 defines a single chain head indicator `gen byte head = !(d & link)` used for `head_ld`, `head_anc`, `head_fs`, `head_nd`, and `head_agree` (lines 89-94). Because the model's own ditto resolution (`namelast_ml_ditto`) runs within an image (lines 6-8), any top-of-image rows (`row == 1` and consecutive `d == 1` rows below it) where `non_ditto_ml == 0` did not receive `image - 1`'s surname in `namelast_ml_ditto`, yet `by chain:` assigns them `head_anc` and `head_fs` from the last `non_ditto_ml == 1` row on `image - 1`. Separately, line 104 defines `gen byte de_headcross = de & head_nd & head_ld!="" & head_cross`, whereas line 110 (`replace namelast_x = head_ld if de & head_nd & head_ld!=""`) omits `& head_cross`.

**Why it matters**  
When `row == 1` of a new image starts a new household (where enumerators always write the surname in full on line 1 of the sheet) but `non_ditto_ml == 0`, `namelast_ml_ditto` has the new household's surname from `row == 1` while `ditto_diag.do` pulls `head_anc` from the bottom of the previous image, causing the household-consistency rule (`lines 179-182`) to replace a correct surname with the previous page's surname (`nt_d_break = 368` in `wy`). Furthermore, omitting `& head_cross` on line 110 means any same-image row with `de & head_nd & head_ld != ""` is filled by `namelast_x` (`dx = 1`, labeled `"Filled by the model fill (cross-image)"` at line 271) while being classified into `de_headother` (labeled `"... other (head is a link break or a missing flag)"` at line 270).

**How to check**  
In `wy/merged_data.dta`, run `count if nt_d_break & head_cross` and `count if d & !head_cross & namelast_ml_ditto != head_ld` after constructing `chain` in `MATCHING/ditto_diag.do` to see how many of the 368 `nt_d_break` records occur on cross-image chains (`head_cross == 1`) or same-image rows where `namelast_ml_ditto` differs from `head_ld`. Also check `count if de & head_nd & head_ld!="" & !head_cross` across states to see where `dx` diverges from `de_headcross`.

**Suggested fix**  
Add `& head_cross` to `replace namelast_x = head_ld if de & head_nd & head_ld!=""` at line 110 (and assert `T_dx == T_de_headcross`), and separate within-image chains from cross-image chains (or verify whether `row == 1` with `non_ditto_ml == 0` started a new surname on its own image) before applying the household-consistency rule (`nt_d_fix`, `nt_d_break`) across image boundaries.

### 4. Table 1 benchmarks `g1` (conditioned on `head_agree==1`) against unconditioned `g2` and `g3`, confounding fill agreement with selection on surname concordance

`g1-benchmark-confounded-by-head-agree-selection` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/ditto_diag.do:127-135, MATCHING/ditto_diag.do:277-298`

**What the code does**  
Lines 127-135 compare surname agreement (`= Ancestry only`, `= FamilySearch only`, `= both`, `= neither`) across `g1 = tgt & dh`, `g2 = tgt & d & namelast_ml_ditto!=""`, and `g3 = tgt & nd & namelast_ml_ditto!=""`. By construction, `g1` conditions on `dh`, which requires `head_agree == 1` (`head_anc == head_fs`). Because Ancestry and FamilySearch also propagate the head's surname down ditto chains, conditioning on `head_agree == 1` drops 98.6% (`1,221 / 1,238` in `wy`) of empty-ditto target rows where the record's own surnames disagree (`namelast != fs_namelast`) and retains almost entirely target rows that disagree only on first name (`namelast == fs_namelast`: `140 / 157 = 89.2%` of `g1` in `wy`). By contrast, `g2` and `g3` do not condition on `head_agree == 1`, so `64.6%` of `g2` and `67.8%` of `g3` are surname-discordant target rows where `= both` is mathematically impossible (`0%`).

**Why it matters**  
Presenting `g1` (`87.90% = both`, `1.91% = neither` in `MATCHING/results/ditto_diag_SMOKE.md:36-42`) side-by-side with `g2` (`35.39% = both`, `13.20% = neither`) and `g3` (`32.17% = both`, `14.65% = neither`) as benchmarks attributes a selection artifact (conditioning on `head_agree == 1`) to the quality of the head-human fill.

**How to check**  
In `MATCHING/ditto_diag.do`, split `g2` and `g3` (or `g1`) by whether the chain head has agreed human surnames (`head_agree == 1` vs `head_agree == 0`) and by whether the record's own human surnames disagree (`namelast != fs_namelast` vs `namelast == fs_namelast`). Compare `g1`, `g2`, and `g3` within the same conditioning set.

**Suggested fix**  
Condition the `g2` and `g3` benchmark columns on `head_agree == 1` (or report the Table 1 breakdown separately for `namelast == fs_namelast` and `namelast != fs_namelast`, as done for `tgt_de` in lines 139-144) so that `g1`, `g2`, and `g3` are compared on the same surname-concordance universe.

### 5. `dup` is computed but not excluded from `link`, so a duplicated ditto row severs the chain for all lower rows in the household

`duplicate-filename-row-breaks-ditto-chain-for-subsequent-rows` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/ditto_diag.do:65-75, MATCHING/ditto_diag.do:85-94`

**What the code does**  
Line 67 defines `bysort roll image row: gen byte dup = parse_ok & _N>1` (and line 65 runs `bysort roll image:` without `, stable`, which permutes tie order before `sort roll image row, stable` at line 69). The comment at lines 79-82 states that a duplicate is a link break that heads a new chain, but line 74 (`gen byte link = parse_ok & roll==roll[_n-1] & ((image==image[_n-1] & row==row[_n-1]+1) | (image==image[_n-1]+1 & row==1 & row[_n-1]==40))`) does not require `!dup & !dup[_n-1]`. When a ditto row `r` (`d == 1`) appears twice (observations `i` and `i+1`), observation `i` has `row[i] == row[i-1] + 1` (`link = 1`), observation `i+1` has `row[i+1] == row[i]` (`link = 0`, `head = 1`, starting a new chain whose head is a ditto row with `head_nd = 0`), and observation `i+2` (`row == r + 1`, a non-duplicate ditto row below `r`) has `row[i+2] == row[i+1] + 1` (`link = 1`, `head = 0`), chaining `row == r + 1` and all lower ditto rows in that household to the duplicate ditto observation `i+1`.

**Why it matters**  
In states where `merged_data.dta` has duplicate `(filename, row)` observations, every ditto row below a duplicated ditto row in the same household gets `head_nd = 0` and `head_agree = 0` (routing empty ditto surnames below it into `de_headother` and disabling `namelast_x`, `namelast_h`, and the household-consistency rule for the rest of the household).

**How to check**  
In any state where `T_dup > 0`, check `count if d & !dup & dup[_n-1]` and `count if de_headother & !dup & head_nd==0` to see how many non-duplicate ditto rows are chained to a duplicate ditto row above them.

**Suggested fix**  
Either deduplicate `(roll, image, row)` in the same way as the linking pipeline (`MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:112-117`) before building chains, or require `!dup & !dup[_n-1]` in `link` at line 74 so duplicate observations cannot participate in chains.
