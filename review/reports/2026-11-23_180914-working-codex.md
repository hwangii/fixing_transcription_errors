## Findings

### 1. The target-flag merge uses `histid`, but the flag file is keyed by `id`

`target-flag-key-mismatch-stops-diagnostic` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/check_mlp_abe_fname_diff.do:38-40, MATCHING/1c_tgt_divided_files.do:63-65`

**What the code does**  
The diagnostic runs `merge 1:1 histid using "`flags'"`, but the sole producer of that file executes `rename histid id` immediately before saving `tgt_flag1940.dta`. The intended operation is to attach target status to each `histid`; Stata instead stops because the using dataset has no `histid` variable.

**Why it matters**  
Nothing after line 38—including the target-status table, second-cleaning test, or examples—can be produced. This makes the new diagnostic unusable, although it does not by itself make an existing paper result wrong.

**How to check**  
In Stata, run `use "$REP_F/enum_date/DATA/INTERMEDIATE/tgt_flag1940.dta", clear`, then `confirm variable id` and `confirm variable histid`; the latter should return r(111). Running the diagnostic should fail at line 38 with the same missing-key error.

**Suggested fix**  
Load the target flag into a tempfile, rename `id` to `histid`, assert `isid histid`, and merge that tempfile. Do not change the permanent flag file without also updating its existing `id`-keyed consumers.

### 2. The test re-cleans an already-abecleaned name and never tests raw model output

`second-cleaning-misdiagnoses-missing-first-pass` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/check_mlp_abe_fname_diff.do:4-6, MATCHING/check_mlp_abe_fname_diff.do:34, MATCHING/check_mlp_abe_fname_diff.do:49-56, MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:173-177, MATCHING/1d_for_mlp_tgtns.do:90-95, MATCHING/1e_tgtns_divided_files.do:18-20`

**What the code does**  
It assigns `f_test = namefrst_true_cleaned` and calls `abeclean f_test l_test`, despite `namefrst_true_cleaned` being the renamed output of the upstream `abeclean ... nickname nonysiis` call. It never loads raw `namefrst_ml`, although the header says the test will run on the raw model name and test whether the MLP names were never cleaned.

**Why it matters**  
A second-pass match with `a_f` can reflect non-idempotent nickname normalization—already acknowledged elsewhere in the repository—rather than a missing first pass. Using this result to explain or repair the 61,959 differences could therefore apply the wrong transformation to linkage inputs.

**How to check**  
Trace the lineage with `rg -n "abeclean namefrst|namefrst.*_cleaned" MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do MATCHING/1d_for_mlp_tgtns.do`. Then merge the raw `namefrst_ml` source used at `1_divide...do:154`, run exactly one pinned `abeclean` pass, and tabulate raw, once-cleaned, stored MLP, twice-cleaned, and ABE values together.

**Suggested fix**  
Compare the raw model transcription with the stored MLP field after exactly one pinned cleaning pass. If the intended question is instead whether `abeclean` is idempotent, relabel the diagnostic and do not interpret a second-pass match as evidence that the first pass was omitted.

### 3. Blank name pairs count as equality with Ancestry and as successful reproduction

`empty-string-ancestry-agreement-inflation` · **minor** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/check_mlp_abe_fname_diff.do:36, MATCHING/check_mlp_abe_fname_diff.do:42-56, MATCHING/0_create_file_for_matching_intgenV4_women_added.do:157-169`

**What the code does**  
The expressions `namefrst_true_cleaned==namefrst`, `a_f==namefrst`, and `f_test_cleaned==a_f` have no nonempty guards. Because the sample only requires the MLP and ABE fields to differ, either one can be blank while also forming a `""==""` pair with Ancestry or the re-cleaned field; the upstream shard reload does not guarantee nonblank names.

**Why it matters**  
The displayed counts can overstate how many discrepant names resemble Ancestry or are reproduced by cleaning, potentially favoring the wrong explanation for the discrepancy. The incidence cannot be determined without the data.

**How to check**  
After constructing the indicators, run `count if mlp_is_anc & namefrst==""`, `count if a_f==namefrst & namefrst==""`, and `count if reproduces & a_f==""`; report these alongside the current counts.

**Suggested fix**  
Require both compared fields to be nonempty in each equality indicator and report blank/blank and one-side-blank cases separately.

### 4. The cleaning diagnostic depends on an undocumented ambient `abeclean` installation

`abeclean-version-not-on-replication-path` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/check_mlp_abe_fname_diff.do:51, replication/config.do:43-44, replication/README.md:109-118, LINKAGE/code/01_abe_jw/reference/abeclean.ado:1-3`

**What the code does**  
The script invokes `abeclean` from whichever ado path happens to be active. Configuration adds only `replication/stata`, and the dependency table does not list `abeclean`; the repository's version 0.26 copy is not placed on the active path.

**Why it matters**  
A clean external installation may stop with command-not-found or use different cleaning and nickname rules. Because the diagnostic is specifically testing name cleaning and its non-idempotence, version drift can change its conclusion.

**How to check**  
On a clean Stata installation, run `do replication/config.do` followed by `which abeclean`. Compare the resolved file and checksum with `LINKAGE/code/01_abe_jw/reference/abeclean.ado`.

**Suggested fix**  
Put the vendored version on the replication ado path, record `which abeclean` in the log, and document its version in the replication requirements.
