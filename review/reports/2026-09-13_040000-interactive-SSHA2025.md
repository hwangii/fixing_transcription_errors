## Findings

### 1. The final display command treats result values as invalid options

`invalid-final-display-syntax` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:62`

**What the code does**  
After macro expansion, `noisily di `denom', `numer1', ...` becomes a command such as `display 100, 20, 30...`. In Stata, text after the first comma is parsed as display options, not additional expressions.

**Why it matters**  
The command errors rather than emitting the denominator and four category counts—the sole output of this script—so the requested comparison result is not produced.

**How to check**  
Run the do-file, or run `display 100, 20` in Stata; it should return a syntax/invalid-option error.

**Suggested fix**  
Display a single formatted string, for example: `noisily di "denom=`denom' ancestry_only=`numer1' fs_only=`numer2' both=`numer3' neither=`numer4'"`.

### 2. Whole-name agreement counts shared blank first or last names as matches

`blank-components-count-as-name-agreement` · **minor** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:39, CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:43, CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:47, CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:51, CODE/comparing_model_transcription_with_anc_fs_SSHA2025.do:55`

**What the code does**  
Eligibility requires only one nonempty field per commercial source, but each category then uses componentwise equality. Thus, for example, `namefrst==namefrst_ml` is true when both are `""`; a surname-only record can therefore be classified as a full-name match based solely on the surname.

**Why it matters**  
This can inflate the ‘Ancestry only,’ ‘FamilySearch only,’ and ‘both’ counts, and changes their interpretation from agreement on a complete two-field name to agreement on whichever field happens to be populated.

**How to check**  
Within each `merged_data.dta`, tabulate the four categories separately for observations where any compared component is blank; e.g., count eligible records with `namefrst=="" | fs_namefrst=="" | namefrst_ml=="" | namelast=="" | fs_namelast=="" | namelast_ml_ditto==""`.

**Suggested fix**  
Either restrict a whole-name comparison to nonempty first and surname fields for all relevant sources/model outputs, or calculate and report first-name and surname agreement separately for partial-name records.

### 1. `invalid-final-display-syntax` — REBUTTED

**Codex was wrong**, despite marking this `verified`. It claimed
`display 100, 20, 30` parses everything after the first comma as options and
errors. Tested in Stata/MP 15.1 on this machine:

```
. capture noisily display `denom', `numer1', `numer2', `numer3', `numer4'
100 20 30 40 50

. display "rc = " _rc
rc = 0
```

Return code 0, all five values printed. In `display`, a comma separates
directives and emits a space; it does not begin an options clause. The commas
are in fact load-bearing — without them, `display 100 20` prints `10020`:

```
. capture noisily display 100 20
10020
```

No change needed at line 62. This is the failure mode CLAUDE.md warns about:
Codex reasoning about Stata semantics from general-language intuition and
reporting the result with unearned confidence.

### 2. `blank-components-count-as-name-agreement` — CONFIRMED, open

Verified by reading the source, and found independently before this review ran.
Line 39 admits a record when *either* name field is non-empty in each source,
but lines 43–55 require *both* components to match, and Stata evaluates
`"" == ""` as true. A surname-only record is therefore scored as a full-name
match on the strength of the surname alone.

Codex rated this `minor`. That understates it: this is the script that produces
the headline Ancestry-vs-FamilySearch comparison, and the bias is not symmetric
across the two sources if their blank rates differ. Severity should be read as
**major**, pending the one check that settles the magnitude:

```stata
count if (namefrst!=""|namelast!="") & (fs_namefrst!=""|fs_namelast!="")
count if (namefrst!=""|namelast!="") & (fs_namefrst!=""|fs_namelast!="") ///
    & (namefrst=="" | namelast=="" | fs_namefrst=="" | fs_namelast=="")
```

The second count over the first is the share of the denominator exposed to the
inflation. If it is negligible, this is a footnote; if not, every rate this
script reports moves.
