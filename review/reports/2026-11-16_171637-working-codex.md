## Findings

### 1. The women’s model-name-present table labels valid first-name transcriptions as cell 4 missing

`women-cell4-mislabels-present-first-names` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_jw.do:148-150, MATCHING/profile_names_jw.do:197-199, MATCHING/profile_names_build.do:46-53`

**What the code does**  
`hasml` requires only `hm_f` for women: `gen byte hasml = (men & hm_f & hm_l) | (wom & hm_f)`. But inherited `cell==4` means either raw model field is absent because `ml_ok = namefrst_ml!="" & namelast_ml_ditto!=""`. Thus a woman with a usable model first name but no model surname passes the new sample while remaining in cell 4. The generated prose instead says group 4 is “empty or near-empty” and describes it as “missing,” although the women’s table scores only her present first name.

**Why it matters**  
The new slide-facing table can report a nonzero cell-4 row containing valid model first names and first-name agreement scores, while readers are told that row represents missing model names. This changes the interpretation of both its N and its performance statistics; the uncommitted review artifact reports hundreds of thousands of such observations, but that count could not be independently reproduced here.

**How to check**  
In Stata, after constructing `hasml`, run `count if wom & has_dmonth & hasml & cell==4` and `count if wom & has_dmonth & hasml & cell==4 & hm_f`; then tabulate raw surname missingness within that group before dropping `hm_f`/`hm_l`.

**Suggested fix**  
For the women’s first-name table, define a first-name-specific cell classification whose missing category depends only on the model first name, or relabel the existing groups explicitly as full-name cells and state that women in cell 4 can have a present, scored first name but a missing surname.

### 2. “Ours+Anc” is not constructed with exactly the linkage pipeline’s fallback rule

`fallback-rule-does-not-exactly-match-linkage-input` · **minor** · claims-vs-code · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_jw.do:105-111, MATCHING/profile_names_jw.do:197, MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:168-170`

**What the code does**  
The new table falls back when `strtrim(namefrst_ml)==""` or `strtrim(namelast_ml_ditto)==""`. The linkage construction cited by the prose falls back using the raw tests `namefrst_true==""` and `namelast_true==""`. Whitespace-only model strings therefore use Ancestry in this table but not necessarily in the linkage input; conversely, nonblank punctuation that normalizes to empty is not filled here and receives a zero score.

**Why it matters**  
If either value pattern exists, the reported “Ours+Anc” statistics do not describe exactly the New transcription used in the linkage tables, contrary to the generated explanation. The size and direction of the numerical difference depend on unseen data.

**How to check**  
Before normalization, count raw-nonempty trimmed-empty model fields. After normalization, count trimmed-nonempty fields whose normalized `cf_ml` or `cl_ml` is empty. Recompute the table under raw-empty, trimmed-empty, and normalized-empty fallback rules and compare the means.

**Suggested fix**  
Choose one documented rule. Use raw `==""` to reproduce the linkage input exactly, or normalize first and fall back on normalized emptiness if the intended estimand is usable names; revise the generated prose accordingly.
