### 1. The new required sample file is absent from machine-B preflight and input hashing

`new-sample-artifact-omitted-from-replication-controls` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `LINKAGE/code/01_abe_jw/linkage_analysis.do:48, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:45, LINKAGE/code/prep/build_linkage_sample1940.do:16-18, replication/run_machineB.do:44-69, replication/hash_inputs_machineB.py:1-34`

**What the code does**  
Both table scripts now read `local sample_f "$D_FLAGS/linkage_sample1940.dta"`, but the file is built on machine A and must be manually copied to machine B. The machine-B preflight still checks the superseded `ipums_fs_names_for_Deaglan1940.dta` and old 1940 name files, while `hash_inputs_machineB.py` continues to require exactly 17 inputs parsed from that stale list.

**Why it matters**  
A preflight can report that every input is present and then the four-hour table run can fail immediately when the first analysis opens the unlisted sample file. Even when manually copied, this result-determining artifact has no manifest hash, so the reported tables cannot be tied to the frozen input set claimed by the replication package.

**How to check**  
On machine B, run `confirm file "$D_FLAGS/linkage_sample1940.dta"` and then run `replication/Run-MachineB.ps1 -PreflightOnly`; inspect whether the preflight detects the file's absence. Also run `rg -n "linkage_sample1940" replication/run_machineB.do replication/hash_inputs_machineB.py replication/input_manifest_machineB.md`.

**Suggested fix**  
Add `data/names/flags/linkage_sample1940.dta` to `run_machineB.do` preflight and regenerate the machine-B manifest from the revised list. Remove the three superseded inputs if no active table script reads them, update the expected manifest count, and automate or document a checksummed machine-A-to-B transfer rather than relying only on the copy instruction.

### 2. The Old/New MI-match columns change the validator as well as the links

`moving-middle-initial-validator` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `LINKAGE/code/01_abe_jw/linkage_analysis.do:242-254, LINKAGE/code/01_abe_jw/linkage_analysis.do:489-512, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:374-386, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:551-574`

**What the code does**  
For Old links the code sets `miv` to `mi_anc`, while for New links it sets it to `mi_ml`, then computes `count if mi1930 == mi1940`. The resulting values are printed side by side as `MI Match Rate` under `Panel A: Coverage and Link Quality`, even though both the linked pairs and the 1940 validating initial change.

**Why it matters**  
An increase in this row cannot be attributed to improved linkage quality: it can arise because the model re-read the middle initial differently even when the linked pair is unchanged. The table caption and row label do not disclose this moving-validator design, so a reader can interpret the difference as independent validation of the links.

**How to check**  
Run `replication/diagnostics/validation_fixed_initials.do`, which already scores both ABE versions against one fixed 1940 initial, and compare its fixed-validator change with the own-initial change. Apply the same fixed-`mi_anc` and fixed-`mi_ml` calculation to the JW and HLINK pairs before retaining their MI rows.

**Suggested fix**  
Either score Old and New links against the same fixed 1940 initial and report that comparison, or relabel and footnote the existing row explicitly as own-transcription agreement. If retained, present the fixed-validator result alongside it so the link-selection contribution is identifiable.
