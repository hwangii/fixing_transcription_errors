## Findings

### 1. The newly scripted HLINK linkage rates divide matched pairs by eligible persons rather than counting unique linked individuals

`hlink-rates-count-pairs-not-linked-people` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:90-101, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:288-295, replication/claims.toml:511-516`

**What the code does**  
'prep_links' deduplicates only exact (histid1930, histid1940) pairs via 'duplicates drop histid1930 histid1940, force'. When computing the in-denominator linkage rate at lines 288-295, the code merges m:1 on histid (histid1940) with 'men1940' and computes '100*_N/N_men_1940_full'. Because histid1940 is not deduplicated, any 1940 individual matched to multiple 1930 records contributes multiple times to _N, yielding pairs per person rather than distinct persons linked.

**Why it matters**  
The paper draft and claim registry describe 58.06% and 59.52% as 'match rates', leading readers to believe 58.06% of the eligible 1940 population was linked. If multiple links per person exist, the actual share of individuals linked is lower, and before/after comparisons may reflect changes in multiple-matching intensity rather than individual linkage coverage.

**How to check**  
In Stata on machine B, after line 291 in 'linkage_analysis_newlinks.do', run 'duplicates report histid' to count duplicate 1940 persons. Then compare '_N' with 'unique histid' or 'egen tag = tag(histid)' followed by 'count if tag'.

**Suggested fix**  
Decide whether the estimand is pairs-per-person or share-of-persons-linked. If person-level linkage is intended, deduplicate on histid1940 (or keep the primary match via first40==1) before dividing by N_men_1940_full. If pair intensity is intended, explicitly clarify in the text and table that the statistic is matched pairs per 100 eligible persons.

### 2. Scripted age-8+ denominators retain records with missing age due to Stata missing value semantics

`missing-ages-enter-age-eight-denominators` · **MAJOR** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `LINKAGE/code/01_abe_jw/linkage_analysis.do:45-47, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:189-191, replication/claims.toml:487-508`

**What the code does**  
Both scripts filter the 1940 census extracts using 'keep if age >= 8' and record _N as N_men_1940_full via repnum (linkDenomAbe and linkDenomHlink). In Stata, numeric missing values (. through .z) evaluate as larger than any number, so records with missing age evaluate as true for 'age >= 8' unless '& !missing(age)' is enforced.

**Why it matters**  
The claim registry describes these denominators as men (or men and women) 'aged 8 and above' (57,589,273 and 115,030,746). If missing ages exist in the input extracts, the denominators are inflated and every match rate computed against them is understated.

**How to check**  
On machine B, load names1940 in each script and run 'count if missing(age)' and 'count if age >= 8 & !missing(age)'. If missing(age) > 0, the denominator changes.

**Suggested fix**  
Replace 'keep if age >= 8' with 'keep if age >= 8 & !missing(age)' in both 'linkage_analysis.do' and 'linkage_analysis_newlinks.do', verify whether any observations are dropped, and document the missing-age handling explicitly.

### 3. The automated replication runner does not verify byte-identical reproduction of all five Deaglan tables

`five-table-byte-identity-not-checked-by-runner` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `replication/README.md:200-202, HANDOFF.md:12-14, replication/extract_deaglan_tables.py:35, replication/extract_deaglan_tables.py:90-104`

**What the code does**  
HANDOFF.md and replication/README.md state that '.\replication\Run-MachineB.ps1 reproduced all five of Deaglan\'s tables byte-identical (SHA-256)'. In the code, Run-MachineB.ps1 delegates table comparison entirely to extract_deaglan_tables.py. However, extract_deaglan_tables.py only defines TABLES = ['abe_jw', 'abe_jw_restricted', 'hlink', 'hlink_restricted'], completely omitting the 5th table ('linkage_table_mortality_bunmd.tex'). Additionally, read() normalizes CRLF to LF ('raw.replace("\r\n", "\n")') and performs string equality comparison rather than a SHA-256 hash or byte-level comparison.

**Why it matters**  
The central replication claim that all five tables reproduced byte-for-byte is not actually verified or enforced by the automated runner. A future run where mortality fails or where whitespace/encoding silently mutates would report success in Run-MachineB.ps1.

**How to check**  
Inspect extract_deaglan_tables.py:35 to confirm TABLES contains only 4 elements and lacks mortality. Check read() at line 48 to observe line-ending replacement.

**Suggested fix**  
Include 'linkage_table_mortality_bunmd.tex' in the reproduction check (either in extract_deaglan_tables.py or a dedicated verification step in Run-MachineB.ps1), and compute explicit SHA-256 hashes against deaglan_results/current/ to substantiate the byte-identical claim in the run log.
