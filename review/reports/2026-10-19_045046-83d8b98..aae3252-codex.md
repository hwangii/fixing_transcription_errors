## Findings

### 1. The newly scripted age-8+ denominators retain records with missing age

`missing-ages-enter-age-eight-denominators` · **MAJOR** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `LINKAGE/code/01_abe_jw/linkage_analysis.do:45-47, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:189-191, replication/claims.toml:487-508`

**What the code does**  
Both scripts execute `keep if age >= 8`, then immediately record `_N` through `repnum`. In Stata, numeric missing values exceed 8, so these counts include every record with `age==.`; the registry nevertheless describes them as people “aged 8 and above.”

**Why it matters**  
If either source contains missing ages, the published denominators 57,589,273 and 115,030,746 are too large for the stated population, and every linkage rate using them is understated. The restricted denominators inherit the same contamination through `cn1940_full`.

**How to check**  
On machine B, run `count if missing(age)` immediately after each `use names1940, clear`, and separately tabulate `count if age>=8` versus `count if age>=8 & !missing(age)`; repeat after merging the discordant flag.

**Suggested fix**  
Use `keep if age >= 8 & !missing(age)` in both scripts, regenerate all four denominators and dependent rates, and update the draft and claim registry to the corrected values.

### 2. The scripted HLINK rates divide matched-pair rows by a person denominator without establishing one pair per person

`hlink-rates-count-pairs-not-linked-people` · **MAJOR** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:90-101, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:288-293, replication/claims.toml:511-516`

**What the code does**  
`prep_links` removes only duplicate `(histid1930,histid1940)` pairs via `duplicates drop histid1930 histid1940, force`. The new statistic then computes `100*_N/N_men_1940_full` after restricting pairs to eligible 1940 IDs. It does not reduce to one observation per `histid1940` or assert that `histid1940` is unique.

**Why it matters**  
The reported 58.06% and 59.52% are pairs per eligible person, not necessarily the share of eligible people linked. Any 1940 person appearing in multiple pairs inflates the numerator and can distort both levels and the before/after change.

**How to check**  
Immediately after the merge at line 291, run `isid histid1940`; if it fails, run `duplicates report histid1940` and compare the current `_N` rate with `egen tag=tag(histid1940)` followed by `count if tag`.

**Suggested fix**  
Define the estimand explicitly. For a person linkage rate, count distinct eligible `histid1940` values and assert the intended uniqueness constraints; if pairs per person is intentional, relabel the statistic and draft language accordingly.

### 3. The runner cannot substantiate its claim that all five tables reproduced byte-identically

`five-table-byte-identity-not-checked-by-runner` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `replication/README.md:200-202, HANDOFF.md:12-14, replication/extract_deaglan_tables.py:36, replication/extract_deaglan_tables.py:85-104`

**What the code does**  
The documentation claims that five tables, including mortality, were SHA-256 identical. The comparison script's `TABLES` list contains only `abe_jw`, `abe_jw_restricted`, `hlink`, and `hlink_restricted`; it never compares `linkage_table_mortality_bunmd.tex`. Moreover, `read()` normalizes CRLF to LF before comparison, so its four comparisons are text-equivalence checks rather than SHA-256 byte comparisons.

**Why it matters**  
A successful `Run-MachineB.ps1` does not verify the mortality output at all and does not perform the advertised byte-level test. The central replication claim therefore lacks reproducible evidence in the committed workflow.

**How to check**  
Run `rg -n "mortality|sha|hash" replication/extract_deaglan_tables.py replication/Run-MachineB.ps1`; then independently run `Get-FileHash -Algorithm SHA256` on the regenerated and committed copies of all five table files and compare the hashes.

**Suggested fix**  
Add the mortality filename to a dedicated five-file comparison step, compare raw bytes or explicit SHA-256 hashes, print and retain both hashes in the run log or manifest, and reserve normalized-text comparison for the separate tabular-extraction task.
