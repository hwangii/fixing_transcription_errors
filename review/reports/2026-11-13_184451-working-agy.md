## Findings

### 1. FamilySearch profile names are an endogenous benchmark, not an independent validation of transcription accuracy

`familysearch-profile-reference-is-endogenous` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:1-7, MATCHING/profile_names_build.do:84-101, MATCHING/profile_names_score.do:1-7, MATCHING/profile_names_score.do:20-25`

**What the code does**  
The build script attaches 1940 census records to FamilySearch profiles via unique_ID_to_census_crosswalk1940.dta, and the scoring script compares each census transcription source (Ancestry, FamilySearch census index, ML) against the profile's name. The header calls this 'For the appendix's transcription validation (tab:transcription_accuracy)'.

**Why it matters**  
FamilySearch profiles are curated by users who locate and attach census records using FamilySearch's search engine and record hints, both of which run on FamilySearch's census transcription. Moreover, profile names are frequently created or updated from the attached census records themselves. This creates mechanical agreement between FamilySearch census transcriptions and profile names. Conditioning on cell 1 does not remove this common-source circularity. Presenting this comparison as an accuracy validation misrepresents resemblance to a selected FamilySearch reference as ground truth.

**How to check**  
Tabulate profile-to-census link provenance (e.g. user manual attachment vs hint), record hint attachment dates vs profile creation/edit dates, and compare all three transcriptions against a true blinded, hand-transcribed sample from raw census images.

**Suggested fix**  
Explicitly describe this analysis as agreement with FamilySearch profile references rather than 'accuracy' or 'transcription validation'. Avoid claiming independent validation of accuracy without a blinded, hand-transcribed ground-truth sample.

### 2. Table claims to report the 'Share of records' agreeing with profiles while silently imposing extensive selection filters

`table-claims-share-of-records-with-selected-denominator` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:42-45, MATCHING/profile_names_build.do:88-101, MATCHING/profile_names_score.do:58-60, MATCHING/profile_names_score.do:107, MATCHING/profile_names_score.do:118-132`

**What the code does**  
MATCHING/profile_names_score.do:107 writes 'Share of records whose transcription agrees with the profile, by source.' However, the estimation sample is restricted to records with: (1) 49 states; (2) all four commercial name fields non-empty; (3) unique 1:1 crosswalk attachments; (4) non-conflicting census sex and profile gender; (5) non-empty normalized reference names; and (6) for women's surnames, never-married women with an attached father.

**Why it matters**  
The label 'Share of records' implies the metric applies to all 1940 census records or all discordant records. In fact, it applies only to a highly selected, non-random subpopulation. Records with illegible or unusual names are far less likely to be profile-linked, skewing agreement rates upward relative to the general census population.

**How to check**  
Count total 1940 census records in the 49 states vs the retained sample at lines 45, 101, and 121 in MATCHING/profile_names_build.do and lines 118, 126, 138 in MATCHING/profile_names_score.do. Calculate the cumulative attrition rate.

**Suggested fix**  
Revise the table header and description in MATCHING/profile_names_score.do:107 from 'Share of records' to 'Share among profile-linked, human-complete records with matching gender and usable reference names', and include a documented selection-flow table showing observation counts at each filter step.

### 3. New validation scripts are omitted from the replication master and rely on an unconfigured, hardcoded E: drive path

`profile-validation-omitted-from-replication-and-hardcodes-e-drive` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:27-28, replication/config.do:19-41, replication/run_machineA.do:92-95, replication/run_machineA.do:125-132`

**What the code does**  
MATCHING/profile_names_build.do:27 hardcodes local prof 'E:/multigen_CM/DATA/INTERMEDIATE', bypassing replication/config.do. Additionally, neither MATCHING/profile_names_build.do nor MATCHING/profile_names_score.do is invoked or preflighted by replication/run_machineA.do.

**Why it matters**  
Running the replication pipeline will not reproduce profile_names.dta or MATCHING/results/profile_names.md. On any machine without an E: drive (such as Machine B or an external replication environment), MATCHING/profile_names_build.do fails immediately with exit 601 when attempting to confirm profile files.

**How to check**  
Inspect replication/run_machineA.do and replication/config.do. Notice neither references MATCHING/profile_names_build.do, MATCHING/profile_names_score.do, or an E: drive global. Run rg -n 'multigen_CM|profile_names' replication/.

**Suggested fix**  
Add a configuration global (e.g. REP_E or REP_MULTIGEN) in replication/config.do, add profile inputs to the preflight checks, incorporate profile_names_build.do and profile_names_score.do into replication/run_machineA.do, and add MATCHING/results/profile_names.md to the verification test suite.

### 4. Forced deduplication omits parent_preferred from the key, allowing arbitrary loss of the preferred-father flag

`parent-preferred-flag-dropped-by-forced-deduplication` · **minor** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:209-220`

**What the code does**  
MATCHING/profile_names_build.do:209 runs 'duplicates drop unique_ID parent_no father_ID father_name, force', omitting parent_preferred from the duplicate key. Lines 218-220 then evaluate _pref = lower(parent_preferred)=='true' to select father_pref. If duplicate rows have conflicting parent_preferred values, whichever row happens to be listed first is kept.

**Why it matters**  
If the row with parent_preferred=='true' is discarded, _pref is set to 0 and father_pref becomes missing (or falls back to an arbitrary parent). This alters the surname reference for affected never-married women based purely on file append order.

**How to check**  
Prior to MATCHING/profile_names_build.do:209, run: bysort unique_ID parent_no father_ID father_name: egen byte p_min = min(lower(parent_preferred)=='true'), followed by p_max = max(lower(parent_preferred)=='true'), and count if p_min != p_max.

**Suggested fix**  
Include parent_preferred in the duplicates drop key at line 209, or compute _pref = max(lower(parent_preferred)=='true') by unique_ID parent_no father_ID father_name prior to deduplication.

### 5. Surnames-only scoreblock inadvertently conditions the sample on the profile having a valid first name

`surname-scoreblock-restricts-on-valid-first-name` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:123-130, MATCHING/profile_names_score.do:156, MATCHING/profile_names_score.do:158`

**What the code does**  
In scoreblock, line 126 defines sample eligibility for all non-'first' measures as gen byte `ok' = `svar' & ref_first!='' & ref_`r'!='''. When measure is 'last_last' or 'last_last_pref' (evaluating only surname agreement), `ok' still requires ref_first!=''.

**Why it matters**  
Records where the profile has a valid surname but an empty or unparseable first name are silently dropped from the surname-only validation tables ('Men: surname' and 'Never-married women: surname'), needlessly making the surname sample dependent on first-name presence.

**How to check**  
In profile_names.dta, count if men==1 & ref_last!='' & ref_first==''. Compare count if men & ref_last!='' against N in scoreblock 'Men: surname'.

**Suggested fix**  
In MATCHING/profile_names_score.do:126, condition on ref_first!='' only when kind=='full'. For kind=='last', define ok as `svar' & ref_`r'!='' so surname scoring does not require a valid first name on the profile.

### 6. Gsort on preferred parent set does not break ties, leaving preferred father selection non-deterministic

`non-unique-gsort-tie-in-preferred-father-selection` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:219-220`

**What the code does**  
Line 219 executes 'gsort unique_ID -_pref parent_no' and line 220 assigns 'by unique_ID: gen str father_pref = father_name[1] if _pref[1]==1'. If a profile has multiple entries with identical _pref and parent_no but different father names, gsort does not uniquely determine which row is placed first.

**Why it matters**  
The assigned maiden surname reference father_name[1] depends on arbitrary physical row order in Stata, introducing non-deterministic behavior into the reference construction.

**How to check**  
Examine observations where _pref==1: bysort unique_ID _pref parent_no: gen byte _tie = _N > 1 & _pref==1. Tabulate _tie to check for profiles with tied sort keys.

**Suggested fix**  
Add deterministic secondary tie-breaking sort keys: gsort unique_ID -_pref parent_no father_ID father_name, or explicitly resolve and count multiple preferred father entries.
