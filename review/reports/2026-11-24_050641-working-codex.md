## Findings

### 1. The builder writes an empty 1930 male shard that the ABE matcher will attempt to process

`empty-male-shard-breaks-abe-matcher` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/1f_v26_inputs.do:193-220, MATCHING/2_ABE_matchingV3_christian_torben.do:74-89, MATCHING/2_ABE_matchingV3_christian_torben.do:137-158, MATCHING/extract_diff_diag.log:2368-2383`

**What the code does**  
Inside each women-added shard, the code executes `keep if sex==1` and then unconditionally `save`s the ABE file. The recorded source diagnostic establishes that 1930 `norace511.dta` is women-added-only and contains zero men. The matcher enumerates every A-side file and invokes `abematch` whenever the corresponding B file exists, without checking either file's observation count; the installed `abematch` aborts when file A has no nonmissing IDs.

**Why it matters**  
The v26 ABE rerun will stop at birthplace 511 rather than producing the new 1930–1940 link file, so the intended like-for-like ABE/MLP comparison cannot be generated.

**How to check**  
Run `use "$REP_F/enum_date/DATA/INTERMEDIATE/divided_file1930_women_added/norace511.dta" if sex==1, clear` followed by `count`; after building, repeat on `divided_file1930_v26_ans_cleaned/norace511.dta`. Then invoke the v26 ABE matcher and confirm it stops on that shard.

**Suggested fix**  
Within the ABE `preserve` block, save a shard only when `_N>0`. Before launching the matcher, assert that every enumerated A and B shard is nonempty and log the intersected birthplace list.

### 2. The new v26 ABE directory types cannot be appended by the existing linkage pipeline

`v26-types-not-supported-downstream` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/1f_v26_inputs.do:46-58, MATCHING/1f_v26_inputs.do:193-232, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:73-105, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:131-139`

**What the code does**  
The builder writes `divided_file1930_v26_ans_cleaned` and v26 model directories containing `mi_true_cleaned`. The appender instead hardcodes `local typeA "_ans_cleaned"`; its ML whitelist is only `inlist("`type'","_true_cleaned","_tgt_cleaned","_tgtns_cleaned")`. A `_v26_true_cleaned` or `_v26_tgt_cleaned` type therefore falls into the `else` branch and requests `keepusing(mi)`, which those model files do not contain. It also searches for a link directory based on the old 1930 `_ans_cleaned` type rather than the new v26 baseline.

**Why it matters**  
Even after matching succeeds, there is no in-repository route from these v26 inputs to an appended link file, score, table, or paper result. Manual renaming or code edits would make the result irreproducible.

**How to check**  
Run `rg -n "v26" MATCHING replication`; the only consumers are inside the new builder. Compare the link directory produced by `2_ABE_matchingV3_christian_torben.do 1930 1940 "_v26_ans_cleaned" 1 "_v26_true_cleaned"` with the directory that the current appender constructs when given `_v26_true_cleaned`.

**Suggested fix**  
Extend the appender to accept explicit A- and B-side directory types, recognize the v26 model types as carrying `mi_true_cleaned`, and add a guarded runner that builds, matches, appends, scores, and gates the v26 results end to end.

### 3. Outputs labeled v26 depend on whichever ambient abeclean happens to resolve

`abeclean-version-not-enforced` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/1f_v26_inputs.do:1-16, MATCHING/1f_v26_inputs.do:61-64, MATCHING/1f_v26_inputs.do:148-155, MATCHING/1f_v26_inputs.do:234, MATCHING/marshall_diag.log:188-189`

**What the code does**  
The script runs `which abeclean`, then calls `abeclean`, but never reads or asserts its version. The diagnostic `count if f_ans=="marshall" & !strpos(lower(namefrst_ans),"marsh")` is merely displayed; a nonzero count does not stop the run. Thus an older cleaner can still write files named `_v26` and print that they were cleaned by 0.26.

**Why it matters**  
The entire rebuild exists because an older cleaner changed roughly 285,000–290,000 first names per year. A machine with that older command would silently recreate the defect while producing apparently authoritative v26 inputs. The current machine's installed file is 0.26, but that dependency is neither archived nor enforced for replication.

**How to check**  
In Stata run `which abeclean`, open the resolved ado, and inspect its header; the existing log shows that `which` prints only the path. Also verify that `replication/stata` contains no pinned `abeclean.ado`, and test that the script has no assertion on `nmar`.

**Suggested fix**  
Archive or install a checksum-pinned abeclean 0.26 through the replication setup, assert the resolved file/version before reading data, and make the Marshall diagnostic a failing gate when it indicates the old bug.
