## Findings

### 1. The FamilySearch columns conceal how often FamilySearch names are actually used

`familysearch-columns-hide-selective-fallback` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:81, MATCHING/fs_avg_performance.do:145-160, MATCHING/1b_fs_divided_files.do:83-87`

**What the code does**  
The divided-file construction records field-level FamilySearch use as `fs_frst_used` and `fs_last_used`, but the scoring merge keeps only `id_A mi1930 mi1940 fiveyr_band`. The resulting columns are labeled `FS 1930`, `FS 1940`, and `FS 1930 & 1940`, although they substitute FamilySearch only where a cleaned FamilySearch field exists and otherwise retain Ancestry.

**Why it matters**  
FamilySearch availability—especially the 1930 mapping—is selective. A linkage rate for this hybrid rule cannot be interpreted as the performance of FamilySearch names without reporting exposure, and differences across years may partly reflect different FamilySearch coverage rather than transcription quality.

**How to check**  
Merge the analysis sample to each link file retaining `fs_used1930` and/or `fs_used1940`, then run `tab fs_used1930 target, missing` and `tab fs_used1940 target, missing`; repeat among `fiveyr_band==1`. Also calculate linkage rates separately for records with and without FamilySearch substitution.

**Suggested fix**  
Carry the `fs_used<year>` indicators into this script, report substitution coverage for each column and sample, and decompose linkage outcomes by whether FamilySearch was used. Label the columns explicitly as FamilySearch-with-Ancestry-fallback unless a pure FamilySearch specification is also shown.

### 2. No master workflow invokes the new scoring script

`familysearch-table-not-in-master-workflow` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/_matching_master_dofile.do:97-101, replication/run_machineA.do:80-105, MATCHING/fs_avg_performance.do:141-168`

**What the code does**  
The matching master builds and appends FamilySearch link files and then exits at line 101; the machine-A master runs a fixed list of CODE and diagnostic scripts. Neither invokes `MATCHING/fs_avg_performance.do`, whose only path to the new TeX result is a direct manual execution.

**Why it matters**  
A replicator following either documented master cannot regenerate the new comparison table. This creates an undocumented manual step and permits the output to become stale relative to rebuilt link files.

**How to check**  
Run `rg -n "fs_avg_performance" -g "*.do" .`; the only matches are inside the script itself, not a caller. Then inspect whether `MATCHING/results/fs_avg_performance.tex` exists after either master completes.

**Suggested fix**  
Add an explicit scoring stage after all five required link files have been built, with preflight checks for those inputs. Alternatively add a documented top-level FamilySearch workflow that builds the links, runs this script, and records the output.

### 3. Validation percentages are presented side by side while their changing denominators are suppressed

`validation-denominators-omitted` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:103-108, MATCHING/fs_avg_performance.do:150-163`

**What the code does**  
The script correctly stores each own-initial denominator as `nv_*` and each fixed-Ancestry denominator as `nva_*`, but the TeX loop writes only `sv_*` and `sva_*` percentages. The denominators vary with the linked set and, for `sv_*`, with which source supplies the initials.

**Why it matters**  
A higher validation share can arise from changes in which linked records have two observable initials, not only from higher agreement. Because every linkage version can have a different denominator, readers cannot assess comparability or the extent of this selection from the generated table.

**How to check**  
Inspect the existing console output at lines 109-110 or add temporary displays of `nv_target_*` and `nva_target_*`; calculate each denominator as a share of linked records and compare it across all five columns.

**Suggested fix**  
Write `nv_*` and `nva_*` into the table, preferably alongside the number of links and validation coverage (`N validated / N linked`). Keep the fixed-Ancestry measure prominent and describe own-source validation as source-dependent.
