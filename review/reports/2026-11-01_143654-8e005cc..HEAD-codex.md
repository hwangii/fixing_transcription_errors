## Findings

### 1. The paper still claims improved transcription quality although no code evaluates names against ground truth

`transcription-quality-claimed-without-ground-truth` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:66-71, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:121-134, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:781-797, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:951-956, CODE/compute_model_agreement_on_discordant.do:123-136, replication/README.md:167`

**What the code does**  
The discordant-record evaluation counts exact equality with commercial transcriptions, for example `namefrst==namefrst_ml & namelast==namelast_ml_ditto` and the analogous FamilySearch expression. Table 1 has no producing code, and the paper itself concedes at lines 304-305 and 951 that neither commercial source is ground truth. It nevertheless calls the rates “transcription accuracies” at line 954 and repeatedly says the method improves transcription quality.

**Why it matters**  
This overstates the paper's central result. The evidence supports improved linkage coverage and independently assessed link outcomes, plus agreement with commercial labels; it does not establish that the underlying name strings are more accurate. The contradiction is especially exposed because the manuscript already states the correct limitation elsewhere.

**How to check**  
Run `rg -n -i "improv.*transcription|transcription quality|transcription accur|ground truth|adjudicat" D:\repos\6638fa0fd89fbec05130caeb\DHTS-2026-10-12.tex` and compare those claims with the equality counts at `CODE/compute_model_agreement_on_discordant.do:123-136` and the Table 1 inventory at `replication/README.md:167`.

**Suggested fix**  
Replace claims of improved name accuracy or transcription quality with the narrower demonstrated claims: agreement with commercial transcriptions and improved linkage coverage/validation. Retain accuracy language only if a blinded, adjudicated name sample with a documented protocol and producing code is added.

### 2. The 104-file manifest substitutes a generated output for an actual full-run preflight input

`manifest-does-not-match-full-run-preflight` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `replication/hash_inputs.py:51-63, replication/run_machineA.do:39-52, replication/README.md:252-256, replication/input_manifest.md:112`

**What the code does**  
`hash_inputs.py` always appends `temp.dta` at line 61 and never includes `CODE/label_socio_demo.do`. In contrast, the full-run preflight always includes `label_socio_demo.do` at `run_machineA.do:43` and includes `temp.dta` only when `$REP_SKIP_REBUILD == 1` at lines 50-52. During a full run, `temp.dta` is generated by `create_figures_SSHA2025.do`, so its manifest row is an output hash rather than a full-run input hash.

**Why it matters**  
The README's statement that the manifest holds hashes of “all 104 inputs” to the 2026-11-01 full run is not literally true. The repository commit tracks the omitted do-file, so this does not invalidate the reported results, but the manifest cannot by itself identify the exact full-run input set and conflates full-run inputs with the skip-rebuild analysis artifact.

**How to check**  
Run `rg -n "label_socio_demo|temp\.dta|REP_SKIP_REBUILD" replication/run_machineA.do replication/hash_inputs.py replication/input_manifest.md`. The two lists have the same count only because `temp.dta` replaces `label_socio_demo.do`.

**Suggested fix**  
Generate separate full-run and `-SkipRebuild` manifests, or label rows as source input, tracked-code input, and generated analysis artifact. For the full-run manifest, exclude `temp.dta`; tie tracked code to the commit hash or include `label_socio_demo.do` explicitly.
