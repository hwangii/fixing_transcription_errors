## Findings

### 1. A single cached file causes incomplete or stale matching stages to be accepted as complete

`partial-cache-produces-incomplete-links` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/_matching_master_dofile.do:67-77, MATCHING/2_ABE_matchingV3_christian_torben.do:98-101, MATCHING/2_ABE_matchingV3_christian_torben.do:137-145, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:73-85`

**What the code does**  
The master skips rebuilding divided files whenever `local built : dir ... files "norace*.dta"` is nonempty. Matching retains an existing output directory, silently skips a birthplace when either current input is missing, and the append stage then reads every existing `norace*.dta` from that directory. Thus one file from an interrupted build is treated as a complete divided dataset, while an old link file can survive after its current input disappears.

**Why it matters**  
An interrupted or changed run can silently omit birthplaces or retain obsolete links, directly changing the FamilySearch link count without an error. This is particularly dangerous because the final display reports only the number of files found, not the expected number or whether they correspond to the current inputs.

**How to check**  
For each year, compare the basenames in `divided_file<yr>_ans_cleaned` and `divided_file<yr>_fs_cleaned`; then compare the intersection of current A/B basenames with the basenames in the matching-output directory. Rerun after temporarily moving one B-side birthplace file and confirm whether its old output remains in the final appended file.

**Suggested fix**  
Rebuild all expected divided files or validate exact basename equality before reuse. Before matching, clear or use a fresh run-specific output directory; after matching, assert that outputs equal the expected A/B intersection and reject extra stale files before appending.

### 2. The FamilySearch benchmark substitutes names only where FamilySearch mapping succeeds and otherwise retains Ancestry

`familysearch-baseline-is-selective-hybrid` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/0b_create_fs_names.do:89-106, MATCHING/1b_fs_divided_files.do:42-56, MATCHING/2_ABE_matchingV3_christian_torben.do:152-158`

**What the code does**  
For 1930, `merge 1:m ... final1930.dta, ... keep(3)` keeps only FamilySearch persons successfully mapped to a `histid`, and ambiguous `histid`s are dropped. The divided-file step starts from Ancestry records and replaces each field only when `fs_namefrst_cleaned!=""` or `fs_namelast_cleaned!=""`; otherwise that field remains Ancestry. Exact linkage is then run on these hybrid `f_name l_name` fields.

**Why it matters**  
The resulting link rate is not the effect of substituting FamilySearch transcription for Ancestry. It combines FamilySearch coverage and successful source mapping, field-specific fallback, and transcription content; coverage is plausibly selective on name difficulty and therefore on linkage success. A comparison against ML or Ancestry can be attributed to the wrong mechanism unless these components are separated.

**How to check**  
Tabulate `fs_frst_used fs_last_used` in each divided file and calculate link rates separately for records with both FamilySearch fields, one field, and neither field on each census side. Also compare FamilySearch coverage by name frequency, race, nativity, and baseline Ancestry linkage status.

**Suggested fix**  
Describe the output as a hybrid fallback policy, not a pure FamilySearch baseline. Report coverage and results by the supplied `fs_*_used` flags, and add a complete-case FamilySearch specification on a fixed population alongside the operational fallback specification.

Add a documented runner for the FamilySearch branch, with preflight checks for all raw and frozen inputs, exact expected file counts, input hashes/provenance, software dependencies, and declared outputs. Either call it from the appropriate replication master or explicitly document it as a prerequisite stage.

### 4. Mixed-source runs silently ignore `name_type_B` outside location 1

`alternate-locations-ignore-later-census-name-type` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/2_ABE_matchingV3_christian_torben.do:24-29, MATCHING/2_ABE_matchingV3_christian_torben.do:50-70, MATCHING/_matching_master_dofile.do:70-77`

**What the code does**  
The optional later-census type is stored in `name_type_B`, but the location-2 and location-3 branches construct `datadirB` with `name_type` rather than `name_type_B`. The FamilySearch master also uses `$REP_F` for its cache directory regardless of `location`, although that global is initialized only in the machine-A configuration.

**Why it matters**  
A mixed run such as FamilySearch 1930 and Ancestry 1940 either reads the wrong B-side directory, fails unexpectedly, or labels output as mixed-source even though both sides used the A-side type. This can produce a mislabeled comparison if the unintended directory exists.

**How to check**  
Invoke the matching script with arguments `1930 1940 "_fs_cleaned" 2 "_ans_cleaned"` and display `$datadirB`; it expands to the `_fs_cleaned` directory rather than `_ans_cleaned`. Also display `$REP_F` before the location-2 FamilySearch branch.

**Suggested fix**  
Use `name_type_B` in every `datadirB` branch and define location-specific intermediate paths consistently. If the new workflow is intentionally machine-A-only, reject every `location!=1` immediately with a clear error.
