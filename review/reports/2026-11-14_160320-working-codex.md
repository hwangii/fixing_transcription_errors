## Findings

### 1. A death month does not establish that the profile name is independent of the attached census index

`death-month-does-not-identify-name-provenance` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:148-154, MATCHING/profile_names_score.do:278-285, MATCHING/profile_names_build.do:152`

**What the code does**  
The code defines `has_dmonth = ustrregexm(lower(deathdate), ...)` and reruns the same profile-name agreement calculations conditional on that flag. It never observes or conditions on the source of `fullname`; the build script merely reads `fullname` and `deathdate` from the same profile scrape row. Thus it identifies profiles containing an externally sourced fact, not independently sourced names.

**Why it matters**  
A profile can retain a name copied from FamilySearch's attached census index while acquiring a death date from another record. Consequently, similar agreement in the death-month subgroup would not eliminate the construction advantage for FamilySearch or validate any interpretation of the comparison as closer to accuracy. This is the central identification concern the proposed robustness appears intended to address.

**How to check**  
For profiles with `has_dmonth==1`, tabulate or manually audit the event/source records that supplied `fullname`, distinguishing names copied from the attached 1940 census from names supported by independent vital records. If source-level provenance is unavailable, compare against a hand-validated name sample instead.

**Suggested fix**  
Relabel this as a suggestive subgroup comparison and explicitly state that it does not establish independent name provenance. For a genuine robustness test, require evidence that the reference name itself comes from an independent event/source, or use a hand-validated reference sample.

### 2. The new death-month results are not produced by the repository's replication master

`profile-results-outside-replication-master` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:280-285, replication/run_machineA.do:92-132, MATCHING/results/profile_names.md:116-128`

**What the code does**  
`profile_names_score.do` now writes six death-month/no-death-month blocks, but `run_machineA.do` invokes only the listed `CODE/` scripts and `MATCHING/fs_avg_performance.do` and `MATCHING/fs_cells.do`; it never invokes `profile_names_build.do` or `profile_names_score.do`. The tracked `profile_names.md` proceeds from the birth-date block directly to Rule (3), so it also does not contain the newly defined results.

**Why it matters**  
A replicator running the documented one-command pipeline will not generate the new appendix robustness results, and the repository currently contains no regenerated output showing what those results are. This allows the paper and tracked output to become stale relative to the analysis code.

**How to check**  
Run `rg -n "profile_names_(build|score)" replication MATCHING/results/profile_names.md` and compare it with `rg -n "Death month|No death month" MATCHING/profile_names_score.do MATCHING/results/profile_names.md`. The calls appear only in the analysis script, not the master or current output.

**Suggested fix**  
Add the profile build/score stages, their required inputs, and `extrname` dependency to a documented replication entry point, or document a separate runnable appendix pipeline. Run it and commit the regenerated `MATCHING/results/profile_names.md` before using the results.

### 3. Persistent split-name caches are invalidated by input date but not by normalization or parsing code changes

`split-name-cache-ignores-code-version` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:113-136`

**What the code does**  
The code reuses each `refs_*.dta` whenever its `c(filedate)` is later than that of `profile_names.dta`: `if ... & t_ref>t_pn local reuse 1`. It stores no hash or version for `pnorm`, `xsplit`, or `extrname`; the comment instead instructs the operator to delete caches manually when normalization changes.

**Why it matters**  
Two runs from the same input data and repository revision can produce different agreement rates depending on whether an older cache happens to exist. A normalization, suffix-list, or parser change can therefore leave published numbers silently stale without raising an error.

**How to check**  
Run `rg -n "refs_|filedate|datasignature|hash|version" MATCHING/profile_names_score.do`. It shows date-based input invalidation and no code/version signature. On a test copy, change a normalization rule while retaining newer cache files and confirm that the script reports `reusing saved split names`.

**Suggested fix**  
Include an explicit cache-format/code-version token in each cache and require it to match, or generate cache filenames from a hash/version of the normalization and splitting specification. Keep the input-date and one-to-one merge checks as additional safeguards.
