## Findings

### 1. Part A labels copied Ancestry names as 1930 model names

`1930-true-cleaned-is-ancestry-not-model` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/marshall_diag.do:10-11, MATCHING/marshall_diag.do:29-30, MATCHING/marshall_diag.do:49-63, MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:145-185`

**What the code does**  
Part A loads `divided_file1930_true_cleaned*`, renames `f_name` and `l_name`, and reports the resulting counts as `1930 model names`. The producer, however, enters its model-transcription branch only when ``yr'==1940`; for 1930 its `else` branch loads `namefrst_ans_cleaned namelast_ans_cleaned` and merely renames them to `namefrst_true_cleaned namelast_true_cleaned`.

**Why it matters**  
Any Part A difference or `marshall` count describes cleaned Ancestry fields from the two census extracts, not an ML transcription. Treating it as evidence that the model or its cleaning differs in 1930 would give the anomaly the wrong source and could prompt an irrelevant model-data correction.

**How to check**  
Pick any common `norace*.dta` shard. Load its `divided_file1930` version, retain `histid namefrst_ans_cleaned namelast_ans_cleaned`, rename `histid` to `id`, merge `1:1 id` with the corresponding `divided_file1930_true_cleaned` shard, and run `assert f_name==namefrst_ans_cleaned & l_name==namelast_ans_cleaned` on matched records.

**Suggested fix**  
Relabel Part A as a comparison of 1930 linking inputs copied from Ancestry, and interpret its counts accordingly. If a 1930 model comparison is intended, load actual 1930 model-output fields and document their producer instead of using `true_cleaned`.

### 2. The diagnostic labels results as abeclean 0.26 without ensuring that version runs

`abeclean-version-label-is-unpinned` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/marshall_diag.do:7-8, MATCHING/marshall_diag.do:23-25, MATCHING/marshall_diag.do:98, MATCHING/marshall_diag.do:111, replication/config.do:43-44, LINKAGE/code/01_abe_jw/reference/abeclean.ado:1-15`

**What the code does**  
The script executes `which abeclean` but neither pins nor asserts the resolved implementation, while its output text says `stored != 0.26`. Configuration adds only `$REP_REPO/replication/stata` to the ado path; the repository's version-0.26 implementation is under `LINKAGE/code/01_abe_jw/reference`, so the command can resolve an ambient installation instead.

**Why it matters**  
The diagnostic is specifically testing cleaner-version drift. A machine with a different installed version can produce different difference counts while the output still identifies the comparator as 0.26, defeating the causal diagnosis and external replication.

**How to check**  
In a fresh Stata session run `do replication/config.do`, `which abeclean`, and `adopath`; compare the resolved file's header or checksum with `LINKAGE/code/01_abe_jw/reference/abeclean.ado`, whose header declares version 0.26.

**Suggested fix**  
Put the vendored 0.26 implementation on a controlled ado path before running the diagnostic and fail if the resolved file/version differs. Derive the displayed version from the verified implementation rather than hard-coding `0.26`.
