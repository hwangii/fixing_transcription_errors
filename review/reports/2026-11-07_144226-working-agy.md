### 1. The scorer requests nonexistent FamilySearch indicators from single-year link files and crashes at runtime

`one-sided-fs-files-request-nonexistent-indicators` · **BLOCKER** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:83-92, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:68-71, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:105-121`

**What the code does**  
In MATCHING/fs_avg_performance.do:84, local fsv is set to "fs_used1930 fs_used1940" whenever substr("`c'",1,2)=="fs", and line 85 requests both via keepusing(id_A mi1930 mi1940 fiveyr_band `fsv'). However, in MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:109-116, gen byte fs_used`y' is generated only when that census year's type equals fstype. Consequently, link1930_1940_fs1930_cleaned_noraceblock0.dta contains only fs_used1930 (fs_used1940 does not exist), while link1930_1940_fs1940_cleaned_noraceblock0.dta contains only fs_used1940 (fs_used1930 does not exist). In addition, line 90 gen byte fs`y'_`c' = fs_used`y'==1 if linked_`c'==1 and line 92 drop ... `fsv' reference the non-existent variables.

**Why it matters**  
When evaluating c=fs30, Stata halts with error 'variable fs_used1940 not found' (r(111)) on line 85. The script terminates prematurely and never writes MATCHING/results/fs_avg_performance.tex.

**How to check**  
In Stata, run: describe fs_used1930 fs_used1940 using "$REP_SNU/enum_date/DATA/INTERMEDIATE/link1930_1940_fs1930_cleaned_noraceblock0.dta". It will report variable fs_used1940 not found. Running MATCHING/fs_avg_performance.do stops with error r(111) at line 85 during the fs30 loop.

**Suggested fix**  
Define fsv conditionally for each combo: for fs12 set fsv to "fs_used1930 fs_used1940"; for fs30 set fsv to "fs_used1930"; for fs40 set fsv to "fs_used1940". In the year loop at lines 89-91, assign fs`y'_`c' = 0 if that year did not use FamilySearch, and drop only the indicators actually kept.

Furthermore, displaying two differing validation rates for Ancestry in Row 3 and Row 5 side by side with no visible footnote or explanation creates the appearance of an internal contradiction or calculation bug.

**How to check**  
Inspect the generated MATCHING/results/fs_avg_performance.tex table. Lines 156-158 contain LaTeX comments (%) that do not compile into document text. Note the mismatch between sva_target_ans and sv_target_ans reported in the console at line 142.

### 4. FamilySearch name usage rates are reported only conditional on linkage, concealing baseline availability in the target population

`familysearch-coverage-unreported-for-target-population` · **minor** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:89-91, MATCHING/fs_avg_performance.do:108-111, MATCHING/fs_avg_performance.do:171-182, MATCHING/1b_fs_divided_files.do:83-87`

**What the code does**  
In lines 89-91, fs`y'_`c' is generated with 'if linked_`c'==1', leaving unlinked records as missing (.). Lines 108-111 summarize fs`y'_`c', so the mean reflects only linked records. The table at lines 171-182 reports 'Links with an FS name in <year> (%)', but does not report the baseline availability of FamilySearch names in the 1940 target or overall sample.

**Why it matters**  
Because FamilySearch names are substituted only when non-empty (falling back to Ancestry otherwise), FamilySearch columns represent a hybrid matching rule. If FamilySearch availability correlates with name rarity or legibility, the linked share reflects both transcription quality and selective linkage of records with available FamilySearch transcriptions. Readers cannot tell whether a higher linkage rate stems from better transcription or differential coverage without knowing baseline availability in the target population.

**How to check**  
Calculate the share of target-sample records with non-empty FamilySearch names in 1940 from census1940_all_labeled_data.dta (or divided files) and compare it with the linked share fs1940_target_c reported in the table.

**Suggested fix**  
Add a row reporting the baseline share of records in the Target and All samples where FamilySearch names were available/used, alongside the linked-record FamilySearch usage shares.
