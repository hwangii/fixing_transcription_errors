## Findings

### 1. The new FamilySearch branch depends on ABE commands that the repository never places on Stata’s ado-path

`abe-commands-not-on-adopath` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/1b_fs_divided_files.do:65, MATCHING/2_ABE_matchingV3_christian_torben.do:44, MATCHING/2_ABE_matchingV3_christian_torben.do:158, replication/config.do:44`

**What the code does**  
The new preprocessing branch directly calls `abeclean fs_namefrst fs_namelast, ...`, and the matcher later calls `abematch ...`. Although repository copies exist under `LINKAGE/code/01_abe_jw/`, configuration adds only `adopath ++ "$REP_REPO/replication/stata"`; assigning `$MatchingDoFiles` does not add that directory to Stata’s command search path.

**Why it matters**  
On a clean Stata installation, the FamilySearch baseline and placebo stop with `command abeclean is unrecognized` before producing any links. Successful execution currently depends on an undocumented command installation in the author’s personal Stata environment, so an external replicator cannot reproduce this new result from the repository.

**How to check**  
Start Stata with an empty PERSONAL/PLUS installation, run `do replication/config.do`, then run `which abeclean` and `which abematch`. Both should fail even though `git ls-files *abeclean.ado *abematch.ado` shows repository copies.

**Suggested fix**  
Add the selected repository ABE implementation to the ado-path in the master/configuration, or copy the required ado files and supporting resources into `replication/stata`. Pin and document which of the reference/comparison implementations produced the results, then make the master confirm both commands with `which` before processing data.

### 2. Existing FamilySearch divided files are reused without validating their contents or inputs

`filename-only-divided-file-cache` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/_matching_master_dofile.do:87-94`

**What the code does**  
The reuse decision compares only `local built : dir ... files "norace*.dta"` with the Ancestry directory’s filename list and skips rebuilding when the two lists match. It does not check row counts, required variables, input `fs_names<year>.dta`, cleaning-code version, or file contents.

**Why it matters**  
Changing or rebuilding the FamilySearch name source—or correcting the cleaning/substitution code—can leave the linkage run using obsolete divided files while reporting them as `complete: reused`. Link counts can therefore depend silently on artifacts from an earlier run rather than the current inputs and code.

**How to check**  
Record the hash of one `divided_file<year>_fs_cleaned/norace*.dta`, rebuild or alter `fs_names<year>.dta`, and rerun the master without deleting the divided directory. It will print `complete: reused`, and the divided-file hash will remain unchanged.

**Suggested fix**  
Rebuild these derived files by default, or store and validate a manifest containing hashes/timestamps for the FamilySearch source, Ancestry source files, relevant code, row counts, and required variables. A `force` option would also make intentional cache reuse explicit.
