### 2. The sentinel-free column silently substitutes Ancestry’s validation initial on affected target records

`own-initial-validation-switch-undocumented` · **minor** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/1e_tgtns_divided_files.do:83-96, MATCHING/score_tgt_links.do:118, MATCHING/score_tgt_links.do:235-249, MATCHING/score_tgt_links.do:325-326`

**What the code does**  
When `sf = f_name=="invalidpred"`, the builder executes `replace mi_true_cleaned = mi_ans if sf`. The scorer assigns that hybrid field to `mi_v_mltgtns` and uses it in `sv_*_mltgtns = count(mi1930==mi1940)/nv_*_mltgtns`. The generated prose explains the existing target-only initial as model-derived on targets and Ancestry-derived elsewhere, but does not state that the new variant uses Ancestry’s initial on sentinel-affected target records.

**Why it matters**  
Any change in the new column’s own-initial “Share validated” combines a change in links with a mechanical change in the validation variable. Without the omitted qualification, readers can interpret that difference as evidence of better link quality; the fixed-Ancestry-initial `sva` row is the comparison that isolates link changes.

**How to check**  
After generating the report, compare the `Share validated, MI` change from `mltgt` to `mltgtns` with the corresponding `Share validated, Ancestry 1940 MI` change. Also use the count printed by `MATCHING/score_tgt_links.do:133-134` to report how many records had their validation initial changed.

**Suggested fix**  
Extend the prose written at line 326 to say that the no-sentinel variant uses Ancestry’s 1940 initial where a first-name sentinel was replaced. Interpret linkage quality primarily with the fixed-Ancestry-initial row or the profile-based rows.
