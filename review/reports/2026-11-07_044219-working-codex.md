### 1. The FamilySearch benchmark is validated against a FamilySearch-derived reference

`familysearch-reference-common-source-risk` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/score_fs_links.do:34, MATCHING/score_fs_links.do:133-161, MATCHING/score_fs_links.do:211-227, CODE/create_linked_sample_for_MLP_training.do:5-17`

**What the code does**  
The scorer names `mlp_training1930_1940.dta` as `true_links`, defines `ver_*` by `histid1930 == true_histid1930`, and outputs the result as `Verified Correct` and `Recall`. The reference is constructed by merging the 1930 and 1940 FamilySearch profile-to-census crosswalks on `unique_ID`.

**Why it matters**  
If FamilySearch census names or search hints helped create those crosswalks, the FamilySearch-name columns and their validation reference share information and errors. Higher verified counts or recall would then overstate the independent evidence that FamilySearch-based linkage is more accurate.

**How to check**  
Document how `unique_ID_to_census_crosswalk1930.dta` and `unique_ID_to_census_crosswalk1940.dta` were created, specifically whether FamilySearch census indexes or names entered candidate generation or adjudication. Repeat the comparison on hand-adjudicated links or a reference built without census-name evidence.

**Suggested fix**  
Describe these outcomes as agreement with the MLP/FamilySearch-derived reference, not independent correctness, unless independence can be established. Add an independent validation or sensitivity sample before using the results as accuracy evidence.

### 2. The FamilySearch columns mix selective field-level fallback with post-link coverage

`post-link-coverage-does-not-identify-familysearch-effect` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/1b_fs_divided_files.do:83-93, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:103-120, MATCHING/score_fs_links.do:201-208, MATCHING/score_fs_links.do:372-377`

**What the code does**  
Upstream code replaces each field only when its cleaned FamilySearch value is nonempty—`replace f_name ... if fs_frst_used` and `replace l_name ... if fs_last_used`—otherwise retaining Ancestry. The scorer collapses the two source indicators to `fs_used<year>` and reports `count if fs_used<year> == 1 / _N` only after restricting to successfully linked pairs.

**Why it matters**  
The displayed columns estimate a FamilySearch-where-available fallback policy, not a pure FamilySearch transcription effect. Because source availability and successful linkage can both be selective, coverage among links cannot show how much of the eligible denominator received FamilySearch fields or whether performance differs for complete, partial, and fallback records.

**How to check**  
Before matching, tabulate `fs_frst_used` by `fs_last_used` for every eligible record in each census and for the common eligible sample. Then reproduce rates and reference categories separately for both-field FamilySearch, partial-FamilySearch, and complete-fallback observations.

**Suggested fix**  
Retain separate first- and last-name indicators, report pre-link coverage over the denominator, and add a common-sample analysis requiring the relevant FamilySearch fields in both censuses. Keep the existing hybrid columns labeled as a fallback policy.
