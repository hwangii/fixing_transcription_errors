### 1. Contradiction shares compare different method-selected subsets of a potentially endogenous reference sample

`method-specific-selected-reference-comparison` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_tgt_links.do:187-203, MATCHING/score_tgt_links.do:300-326, CODE/create_linked_sample_for_MLP_training.do:5-13, LINKAGE/notes/truth_file_provenance.md:28-50`

**What the code does**  
For each link version, the code separately classifies proposed pairs against the FamilySearch-profile file and reports `100*con_`s'_`c'/(ver_`s'_`c'+con_`s'_`c')`. Thus every column conditions on its own set of proposed links that happen to be covered by the reference, rather than comparing methods on fixed common support. The reference itself is created by inner-joining census records attached to the same FamilySearch profile via `merge ... keep(3)` and retaining profiles with complete vital dates.

**Why it matters**  
Reference coverage can vary with transcription difficulty and with resemblance to FamilySearch names. The repository already notes that FamilySearch-based attachment may under-represent poorly indexed records and may favor the model where its names resemble FamilySearch's. Consequently, differences in contradiction shares can reflect changing coverage and composition rather than better links; the target/non-target split does not remove this selection.

**How to check**  
After running the scorer, display `(ver_`s'_`c'+con_`s'_`c')/L_`s'_`c'` for every sample and version. Then recompute correctness indicators on 1940 IDs linked by all four methods and covered by the reference, and separately tabulate added, dropped, and switched IDs; compare those estimates with the existing method-specific shares.

**Suggested fix**  
Report reference coverage beside every column and add a common-support or added/dropped/switched decomposition. Describe the existing ratios as method-specific, reference-covered statistics and explicitly discuss the possible FamilySearch-name selection channel.

### 2. Matches to a FamilySearch-derived reference are labeled “Verified correct” without independent adjudication

`reference-match-labeled-verified-correct` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_tgt_links.do:187-203, MATCHING/score_tgt_links.do:300, MATCHING/score_tgt_links.do:317-321, CODE/create_linked_sample_for_MLP_training.do:5-13`

**What the code does**  
A pair is counted as verified when `person_merge == 3 & histid1930 == true_histid1930`, and recall is `ver_.../(ver_...+FN_...)`. The output labels these rows `Verified correct` and `Recall (%)`. Line 300 discloses that the benchmark is the FamilySearch-profile sample, but the benchmark is constructed from common profile attachments rather than a documented hand-adjudication protocol.

**Why it matters**  
Readers can interpret these labels as independent evidence of true link accuracy. The calculations establish agreement and recovery relative to a selected FamilySearch-derived reference, whose attachments may themselves depend on FamilySearch indexing; they do not establish population correctness or recall.

**How to check**  
Run `rg -n "Verified correct|Recall|unique_ID_to_census_crosswalk|hand.?valid|manual.?valid" MATCHING/score_tgt_links.do CODE/create_linked_sample_for_MLP_training.do LINKAGE/notes/truth_file_provenance.md` and trace the purported verification back to the profile-crosswalk merge; no hand-validation step appears in that lineage.

**Suggested fix**  
Rename the rows to “Matches FamilySearch-profile reference” and “Reference-pair recovery,” and state that the reference is selected and potentially dependent on FamilySearch indexing. Reserve “correct,” “verified,” and population “recall” for independently adjudicated links.
