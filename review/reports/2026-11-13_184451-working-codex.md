## Findings

### 1. FamilySearch profile names are a common-source benchmark, not independent validation

`familysearch-profile-reference-is-endogenous` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:3-7, MATCHING/profile_names_build.do:84-101, MATCHING/profile_names_score.do:20-24`

**What the code does**  
The build keeps census records already attached to exactly one FamilySearch profile via `unique_ID_to_census_crosswalk1940.dta`, and the scorer measures whether each transcription agrees with that profile's name. The source itself acknowledges that users find and attach records through FamilySearch's index and that profile names may be copied from the attached record, yet calls the exercise the appendix's `transcription validation`.

**Why it matters**  
FamilySearch census strings can agree mechanically with profile names because the same strings helped locate or populate the profile. Cell 1 does not remove this endogeneity: it conditions on the model equaling Ancestry and then compares both against a FamilySearch-associated target. These rates identify resemblance to a selected FamilySearch reference, not which transcription is correct.

**How to check**  
Within the profile-linked sample, tabulate agreement by attachment provenance if available—manual attachment, automated hint, and attachment date relative to profile-name edits. Separately hand-read a random stratified set of census images and compare all three transcriptions against that blinded adjudication.

**Suggested fix**  
Describe the table only as agreement with FamilySearch profiles and treat the common-source result as descriptive. For an accuracy claim, add a blinded hand-validated image sample whose selection and adjudication do not depend on any of the three transcriptions.

### 2. The generated table says “Share of records” without disclosing its highly selected denominator

`generated-table-hides-selected-denominator` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:42-45, MATCHING/profile_names_build.do:88-101, MATCHING/profile_names_score.do:107, MATCHING/profile_names_score.do:118-132`

**What the code does**  
Before scoring, the build requires all four commercial name fields to be nonempty and retains only one-to-one census-to-profile attachments. Each score block further requires usable profile reference fields through `ref_first!=""` and, where applicable, `ref_`r'!=""`. The generated prose nevertheless says only `Share of records whose transcription agrees with the profile, by source`.

**Why it matters**  
The denominator excludes records with missing commercial transcriptions, ambiguous profile attachments, absent profile names, and—for surname analyses—missing reference surnames. These exclusions plausibly remove difficult names, so readers could interpret a selected-sample agreement rate as applying to all 1940 records or all profile-linked records.

**How to check**  
Run sequential `count` commands before and after lines 45, 96, 101, 118/126, and 132, reporting both counts and percentages of the initial `histid` universe. Compare name missingness and model agreement across retained and excluded groups wherever observable.

**Suggested fix**  
Add a generated table note stating every inclusion restriction and provide a selection-flow table with counts. Replace `Share of records` with an explicit denominator such as `Share among human-complete, uniquely profile-attached records with a usable profile reference`.

### 3. Neither new validation script is called or preflighted by the replication pipeline

`profile-validation-omitted-from-replication-master` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:22-28, replication/run_machineA.do:47-60, replication/run_machineA.do:92-95, replication/run_machineA.do:125-132`

**What the code does**  
The new build and score scripts are standalone. The machine-A master preflights existing model and linkage inputs and runs its fixed `scripts` list plus `fs_avg_performance` and `fs_cells`; it never invokes `profile_names_build.do` or `profile_names_score.do`. The build additionally introduces an `E:/multigen_CM/DATA/INTERMEDIATE` source that is not represented by a configuration global or master preflight.

**Why it matters**  
A normal replication run cannot produce or verify the proposed appendix result. A missing or stale `profile_names.dta` can therefore leave the appendix table absent or based on an undocumented prior run, while an external replicator has no configured path or provenance for the 133 profile scrapes.

**How to check**  
Run `rg -n "profile_names_(build|score)|profile_names.dta|multigen_CM" replication MATCHING` and inspect `replication/run_machineA.do`; the only executable references are inside the two new scripts themselves.

**Suggested fix**  
Add the profile inputs to the machine-A configuration and preflight, invoke build then score from the master in dependency order, document the scrape provenance and expected file count, and include `MATCHING/results/profile_names.md` in the driver's changed-result failure check.

### 4. Forced deduplication can arbitrarily discard the preferred-parent flag used immediately afterward

`preferred-father-flag-discarded-by-forced-deduplication` · **minor** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:209-220`

**What the code does**  
The code runs `duplicates drop unique_ID parent_no father_ID father_name, force`, omitting `parent_preferred` from the duplicate key. It then constructs `_pref = lower(parent_preferred)=="true"` and selects the first preferred father. If otherwise identical rows disagree on `parent_preferred`, whichever row happens to occur first survives.

**Why it matters**  
Affected never-married women can receive a different or missing `father_pref`, changing their surname reference, their inclusion in the preferred-parent score, and the reported agreement rates. The result depends on append order rather than an explicit conflict rule.

**How to check**  
Before line 209, run `bysort unique_ID parent_no father_ID father_name: egen byte pref_min=min(lower(parent_preferred)=="true")`, similarly compute `pref_max`, then `count if pref_min!=pref_max` and `list unique_ID parent_no father_ID father_name parent_preferred if pref_min!=pref_max`.

**Suggested fix**  
Include `parent_preferred` in the deduplication key, then explicitly detect profiles with conflicting flags and either resolve them by a documented rule or drop and count them before choosing `father_pref`.
