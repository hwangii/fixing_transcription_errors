## Findings

### 1. FamilySearch-linked profile names are an endogenous benchmark, not an independent validation of transcription accuracy

`familysearch-profile-reference-is-endogenous` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:1-7, MATCHING/profile_names_build.do:83-109, MATCHING/profile_names_score.do:25-33, MATCHING/profile_names_score.do:140`

**What the code does**  
Census records are linked to FamilySearch profiles via unique_ID_to_census_crosswalk1940.dta, and each transcription source (Ancestry, FamilySearch census index, ML) is scored against the profile's name. Although the header and markdown note acknowledge that users attach records through FamilySearch's index and may copy names from it, the analysis is intended for the appendix as a benchmark (tab:transcription_accuracy).

**Why it matters**  
FamilySearch profile names are largely created and curated by genealogists who discover and attach 1940 census records using FamilySearch's transcription and search algorithms. This generates mechanical agreement favoring FamilySearch. Furthermore, selection into being attached to a profile strongly correlates with name legibility, commonness, and Anglo-American ethnicity, meaning agreement rates within this linked subsample cannot measure transcription accuracy in the general census population.

**How to check**  
Tabulate link provenance and profile creation dates relative to census attachment dates. Compare agreement rates across name frequency deciles and race/nativity groups. To validate accuracy, conduct a blinded hand-audit of raw census images.

**Suggested fix**  
Frame this exhibit strictly as descriptive agreement with a FamilySearch-linked genealogical reference, not as accuracy or independent validation. For any claim of accuracy, evaluate on an independently sampled, hand-verified ground-truth dataset.

### 3. The sample selection table reports ambiguous crosswalk row counts as numbers of dropped records

`ambiguous-crosswalk-drops-report-rows-as-records` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:91-100, MATCHING/profile_names_score.do:141-150`

**What the code does**  
In MATCHING/profile_names_build.do, lines 94-98 calculate n_xmh = r(N) from count if _mh and n_xmu = r(N) from count if _mu, where _mh flags histids appearing in multiple crosswalk rows and _mu flags unique_IDs appearing in multiple crosswalk rows. In MATCHING/profile_names_score.do, lines 141-150 display these numbers in a markdown table under a records column labeled | ... dropped: record attached to >1 profile | and | ... dropped: profile attached to >1 record |.

**Why it matters**  
A record linked to multiple profiles appears multiple times in the crosswalk, so count if _mh counts crosswalk rows rather than the number of unique records dropped. If a row has both _mh==1 and _mu==1, it is counted in both rows. The column is labeled records, but the reported numbers are non-additive row counts from an external crosswalk, misstating the volume of dropped census records.

**How to check**  
In profile_names_build.do before drop if _mh | _mu, compute distinct histid if _mh, distinct unique_ID if _mu, and count if _mh & _mu. Compare the distinct ID counts to n_xmh and n_xmu.

**Suggested fix**  
Store and report distinct counts of affected histids and unique_IDs, or label the rows explicitly as crosswalk pairs/rows dropped, and report the net union of removed census records.

### 4. Rule (3) robustness conditions sample inclusion on at least one source matching the reference

`rule-3-conditions-sample-on-outcome` · **minor** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:215-217`

**What the code does**  
Line 217 runs scoreblock "Rule (3): men, at least one source matches first name and surname" men full_last "(mf_anc & mlast_anc) | (mf_fs & mlast_fs) | (mf_ml & mlast_ml)". This restricts the sample to observations where at least one of the three transcription sources agrees with the profile reference.

**Why it matters**  
Conditioning on the dependent variable (whether any transcription matches the reference) excludes records where all three transcriptions disagree with the profile. In cell 1 (where ML agrees with Ancestry and both disagree with FamilySearch), this condition guarantees that Ancestry agreement and FamilySearch agreement sum to exactly 100%, mechanically exaggerating agreement rates and distorting comparisons.

**How to check**  
Tabulate the share of records dropped by Rule (3) across cells 0 through 4. Verify that in cell 1, the sum of Ancestry and FamilySearch agreement is forced to 100%.

**Suggested fix**  
Retain this only as an explicitly labeled sensitivity check illustrating the upper bound under the assumption that one source is always correct, and clarify in the text that it conditions on the outcome.
