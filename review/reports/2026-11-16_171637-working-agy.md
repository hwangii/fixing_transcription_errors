## Findings

### 1. Baseline table 'Women, death month on profile: first name' condition erroneously restricted by hasml

`women-baseline-condition-restricted-by-hasml` · **BLOCKER** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_jw.do:199`

**What the code does**  
In MATCHING/profile_names_jw.do:199, specification 5 in the spec loop is defined as 'wom&has_dmonth&hasml|Women, death month on profile: first name'. The condition includes '&hasml', restricting the sample to records where the model first name is non-empty after normalization, instead of using the unrestricted baseline condition 'wom&has_dmonth' matching its title and the check at lines 173-174.

**Why it matters**  
The markdown table generated under '## Women, death month on profile: first name' will not report the baseline sample of women with a death month on profile (N = 23,365,543), but an undocumented subpopulation restricted to records with a model first name. It silently duplicates the restricted sample from specification 2 under an unrestricted heading, altering the sample size and all agreement and similarity metrics.

**How to check**  
Inspect MATCHING/profile_names_jw.do:199 to see the condition 'wom&has_dmonth&hasml' assigned to the spec titled 'Women, death month on profile: first name', or compare 'count if wom & has_dmonth' against 'count if wom & has_dmonth & hasml'.

**Suggested fix**  
In MATCHING/profile_names_jw.do:199, change 'wom&has_dmonth&hasml|Women, death month on profile: first name' to 'wom&has_dmonth|Women, death month on profile: first name'.

### 2. Women's 'model first name present' table retains records in cell 4 and mislabels them as missing model transcriptions

`women-cell4-mislabels-present-first-names` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_jw.do:148-156, MATCHING/profile_names_jw.do:197-200, MATCHING/profile_names_build.do:46-53`

**What the code does**  
hasml for women requires only that the model produced a first name: 'gen byte hasml = (men & hm_f & hm_l) | (wom & hm_f)'. However, variable cell is imported from profile_names.dta, where cell==4 was defined using both names: 'replace cell = 4 if disc & !ml_ok', with 'ml_ok = namefrst_ml!="" & namelast_ml_ditto!=""'. Discordant women where the model produced a first name but no surname have hasml==1 and cell==4. When generating the table for 'wom&has_dmonth&hasml|Women, death month on profile, model first name present: first name', group 4 is tabulated, despite the markdown text stating that in model-names-present sections 'no source is scored on an empty model name; group 4 is then empty or near-empty' and 'group 4 (missing) refers to the model names alone'.

**Why it matters**  
In the women's model-first-name-present table, group 4 is not empty or near-empty (containing over 500,000 records in the baseline population). These records have present model first names that are scored and achieve positive agreement/similarity in row 4, directly contradicting the text describing group 4 as representing missing model transcriptions.

**How to check**  
In Stata, run 'count if wom & has_dmonth & hasml & cell==4' and 'sum xf_ml if wom & has_dmonth & hasml & cell==4' to confirm non-zero count and positive agreement in cell 4.

**Suggested fix**  
For the women's first-name table, either construct a first-name-specific cell classification where cell 4 reflects missingness of namefrst_ml alone, drop group 4 from the table when scoring hasml, or clarify in the header text that group 4 reflects missingness of either name in the full-name classification rather than missingness of the scored first name.

### 3. Fallback rule for 'Ours+Anc' does not match the linkage cleaning pipeline and fails to fall back on strings that normalize to empty

`fallback-rule-diverges-from-linkage-and-normalization` · **minor** · claims-vs-code · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_jw.do:105-111, MATCHING/profile_names_jw.do:197, MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:168-170`

**What the code does**  
Lines 108-111 define fallback indicators fb_f = strtrim(namefrst_ml)=='' and fb_l = strtrim(namelast_ml_ditto)=='' on raw strings before normalization, and gen namefrst_mf = cond(fb_f, namefrst, namefrst_ml). The linkage pipeline in MATCHING/1_divide_and_clean_everyoneV5_women_addedV2.do:169-170 uses raw un-trimmed tests namefrst`name_type'=='' without strtrim. Additionally, strings consisting solely of punctuation, numbers, or titles (e.g. '.' or '(dr)') evaluate to false under strtrim()=='', preventing fallback to Ancestry, but normalize to empty under pnorm, receiving a 0 score in jwpair.

**Why it matters**  
The markdown header claims 'Ours+Anc = ours with Ancestry's name wherever the model field is empty, field by field, as the linkage tables' New transcription'. In the presence of whitespace-only or punctuation-only transcriptions, the Ours+Anc metric does not exactly match the linkage tables' New transcription, nor does it replace uninformative model transcriptions with Ancestry's valid names.

**How to check**  
Count records where strtrim(namefrst_ml)!='' but cf_ml=='' to see how many non-fallback model names normalize to blank.

**Suggested fix**  
Define the fallback rule after pnorm so any model transcription that normalizes to empty falls back to Ancestry's normalized name, or align the raw string check exactly with the linkage tables, and document the behavior accurately.
