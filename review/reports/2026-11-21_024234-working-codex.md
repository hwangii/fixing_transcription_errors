## Findings

### 1. The image-clustering comparison mechanically includes each record’s own failure

`self-inclusive-image-failure-diagnostic` · **minor** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/nomodel_diag.do:33-36, MATCHING/nomodel_diag.do:104-110`

**What the code does**  
The code computes `img_fail = mean(fail)` within `filename`, including the focal record, and then reports `count if ftype==t & img_fail>0.5`. It therefore conditions a record’s failure type on an image statistic partly constructed from that same outcome. For an image containing one target record, the statistic is deterministically 100% for a failed record and 0% for a successful record.

**Why it matters**  
This mechanically exaggerates evidence that missing model output clusters by image, especially for images with few target records. If the diagnostic is used to support an explanation based on image quality or segmentation, the reported comparison is not independent evidence for that explanation.

**How to check**  
After constructing the appended dataset, run `gen double img_fail_loo=(img_fail*img_n-fail)/(img_n-1) if img_n>1`, generate indicators for `img_fail>0.5` and `img_fail_loo>0.5`, and compare `tab ftype mostly,row` with `tab ftype mostly_loo if img_n>1,row`; also run `count if img_n==1`.

**Suggested fix**  
Use the leave-one-out failure share for record-level comparisons and report singleton images separately, or collapse to one observation per `st filename` and report an explicitly image-level clustering statistic.

### 2. The documented standalone command cannot run from a clone outside the author’s D: path

`absolute-config-bootstrap` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/nomodel_diag.do:17, MATCHING/nomodel_diag.do:21-23`

**What the code does**  
The documented command invokes the script without preloading globals, after which `if "$REP_REPO"==""` executes `do "D:/repos/fixing_transcription_errors/replication/config.do"`. Thus the centralized configuration cannot itself be reached when the repository is cloned elsewhere.

**Why it matters**  
An external replicator must edit the analysis script before running it, even after configuring the repository’s intended central path file. This is a genuine but easily repaired portability break in the new standalone diagnostic.

**How to check**  
Run `rg -n 'D:/repos|REP_REPO|REP_SNU' MATCHING/nomodel_diag.do replication/Run-Stata.ps1` and compare the documented invocation with the working directory established by `Run-Stata.ps1`.

**Suggested fix**  
Under the documented driver, load `../replication/config.do` relative to the script’s working directory, or have the driver pass the repository root explicitly; keep machine-specific data roots solely in `replication/config.do`.
