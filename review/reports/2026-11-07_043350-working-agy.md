### 1. Replication gate verifies link counts but fails to check baseline recall or middle-initial match rates

`replication-gate-omits-recall-and-mi` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_fs_links.do:23-25, MATCHING/score_fs_links.do:214-228, MATCHING/score_fs_links.do:235-242, MATCHING/score_fs_links.do:327-341, MATCHING/score_fs_links.do:360-385`

**What the code does**  
The script asserts that the Ancestry and ML columns must reproduce the paper before writing results, but its check (bad) evaluates only denominators, verified/unverifiable/contradicted counts, and net added/removed categories (k_samp_c != p_samp_c_k and d_k_samp_true != p_samp_d_k). It never compares recall_samp_c or mi_rate_samp_c against paper benchmarks before printing 'REPLICATION PASSED' and writing the table.

**Why it matters**  
If false negative counts in true_pairs change or middle initial cleaning in the divided files drifts, recall and mi_rate in the output LaTeX table can diverge from the published paper without tripping the gate, compromising the stated guarantee that baseline columns match the paper.

**How to check**  
Compare the computed recall_full_ans, recall_full_true, mi_rate_full_ans, and mi_rate_full_true scalars against the published table cells; alter a middle initial in a divided file and verify that the gate still prints 'REPLICATION PASSED'.

**Suggested fix**  
Add hardcoded scalar targets for Ancestry and ML baseline recall and middle-initial match rates, and include them in the fail-closed if bad { exit 9 } check.

### 3. Scoring FamilySearch transcriptions against FamilySearch-derived profile links introduces common-source confounding

`familysearch-reference-common-source-risk` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/score_fs_links.do:34, MATCHING/score_fs_links.do:120-149, MATCHING/score_fs_links.do:198-214, CODE/create_linked_sample_for_MLP_training.do:5-17`

**What the code does**  
The code treats agreement with mlp_training1930_1940.dta as ground truth (Verified Correct and Recall). Upstream in CODE/create_linked_sample_for_MLP_training.do, that reference is constructed by linking FamilySearch tree profiles across censuses via unique_ID_to_census_crosswalk1930.dta and 1940.dta.

**Why it matters**  
If FamilySearch profile-to-census crosswalks were generated or verified using FamilySearch census indices or transcriptions, links generated from FamilySearch names will share common errors and search selection with the evaluation reference, mechanically inflating verified counts and recall relative to independent transcriptions.

**How to check**  
Inspect the documentation and provenance of unique_ID_to_census_crosswalk*.dta to determine whether FamilySearch census transcriptions guided profile attachment; evaluate FamilySearch and Ancestry links on an independently hand-curated census sample.

**Suggested fix**  
Clarify in table notes and manuscript text that Verified Correct reflects agreement with the FamilySearch-derived MLP genealogical links rather than absolute ground truth, and test robustness on an independent validation set.

### 4. Field-by-field Ancestry fallback conflates FamilySearch transcription quality with selective Ancestry coverage

`hybrid-fallback-confounds-familysearch-comparison` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/score_fs_links.do:188-196, MATCHING/score_fs_links.do:350, MATCHING/score_fs_links.do:361-362, MATCHING/1b_fs_divided_files.do:83-87, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:110-112`

**What the code does**  
Upstream divided files substitute FamilySearch names only when non-empty, falling back to Ancestry field by field. In score_fs_links.do, fs_used flags any link with at least one FamilySearch field (fs_frst_used | fs_last_used). The resulting table presents columns labeled 'FS 1930 & 1940', 'FS 1930', and 'FS 1940' that contain heterogeneous mixtures of pure FamilySearch, single-field FamilySearch/Ancestry hybrids, and pure Ancestry fallback records.

**Why it matters**  
Missingness in FamilySearch transcriptions is non-random with respect to page quality and name rarity. Because partial and missing records selectively retain Ancestry transcriptions, differences in match rates and verification across columns reflect both transcription accuracy and selective fallback composition.

**How to check**  
Tabulate joint coverage of fs_frst_used and fs_last_used on both census sides, and compare match and verification rates across pure FamilySearch pairs, hybrid pairs, and pure Ancestry fallback pairs.

**Suggested fix**  
Disaggregate coverage reporting into first-name, last-name, and joint coverage, and report a sensitivity analysis restricted to the balanced sample where FamilySearch transcriptions exist for both fields in both censuses.
