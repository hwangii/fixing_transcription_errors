## Findings

### 1. The paper claims improved transcription quality although the code measures only agreement and linkage outcomes

`transcription-improvement-claimed-without-name-ground-truth` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:66-71, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:121-131, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:278-304, CODE/compute_model_agreement_on_discordant.do:116-130`

**What the code does**  
The disagreement evaluation counts exact resemblance to commercial transcriptions, using conditions such as `namefrst==namefrst_ml & namelast==namelast_ml_ditto` and the corresponding FamilySearch expression. It does not compare the machine output with an adjudicated image transcription. The draft itself concedes at lines 278-282 and 304 that these are agreement rates and that no blinded adjudication has been conducted, yet the abstract and contribution statements say the method “improves name transcription,” “improve[s] transcription quality,” and achieves “dramatic improvements” in data construction.

**Why it matters**  
Improved agreement or improved downstream linking does not establish that the underlying names are more accurately transcribed. This is the paper's headline contribution, and the present wording overstates the available evidence in exactly the area most vulnerable to referee challenge.

**How to check**  
Run `rg -n -i "improv.*transcription|transcription quality|higher accuracy|accurate transcription" D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex` and compare each occurrence with the only direct name comparisons at `CODE/compute_model_agreement_on_discordant.do:116-130`. Confirm that no code or completed table compares model output to blinded, image-adjudicated names.

**Suggested fix**  
Until the planned validation is completed, consistently describe the demonstrated result as improved linkage outcomes and agreement with commercial transcriptions. Reserve “more accurate transcription,” “improved transcription quality,” and equivalent language for results against a preregistered or blinded adjudicated-name sample.

### 2. The repository does not generate the link files underlying the headline or robustness results

`linking-and-validation-results-consume-opaque-inputs` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `CODE/create_figures_SSHA2025.do:61-78, CODE/create_figures_SSHA2025.do:151-207, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:413-434, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:551-580`

**What the code does**  
The main analysis merges precomputed files named `link1930_1940_ans_cleaned_noraceblock0.dta` and `link1930_1940_true_cleaned_noraceblock0.dta`, then defines outcomes as `_merge==3 & fiveyr==1`. It computes the published rates from those flags, but CODE contains no producer implementing the claimed exact-name, birthplace, ±2-year, and uniqueness rules. It also contains no generating code for the ABE, Jaro-Winkler, HLINK, or genealogical verification tables described at paper lines 551-580.

**Why it matters**  
The arithmetic after the merges can be checked, but the substantive classifications—who is linked, verified, contradicted, or unverifiable—cannot be checked against the paper's stated algorithms. These opaque inputs support the 119 percent headline result and the claimed cross-algorithm validation, so a referee or replication reviewer cannot establish that the descriptions match the computations.

**How to check**  
Run `rg -n -i "link1930_1940|HLINK|Verified Correct|Directly Contradicted|Jaro-Winkler|fiveyr" CODE`. The matches consume link outputs or discuss results; none constructs the two main link files or the four robustness tables from raw records.

**Suggested fix**  
Add the scripts and exact commands that generate every consumed link file and the four robustness/validation tables, including sample restrictions, uniqueness rules, genealogical merge keys, and contradiction classification. Then regenerate the tables from those scripts and connect them to the repository entry point.

### 3. The conclusion claims reduced empirical bias although the code estimates only subgroup linkage rates

`bias-reduction-claim-not-estimated` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:750-765, CODE/create_figures_SSHA2025.do:310-330, CODE/compute_subgroup_linkage_rates.do:20-28`

**What the code does**  
For each observed subgroup the code summarizes `linked_before` and `linked_after` and reports `100*(`a'/`b'-1)`. It does not compare linked-sample composition with the underlying population, estimate an outcome on linked versus full data, or calculate bias in any empirical estimand. Nevertheless, the conclusion says the results “reduce biases in the empirical findings derived from” linked data and that the method reduces demographic and geographic biases.

**Why it matters**  
Higher linkage rates for selected groups can improve coverage but do not by themselves show reduced representativeness bias or reduced bias in downstream estimates. Differential false links or selection within each broad subgroup could leave bias unchanged or worsen it.

**How to check**  
Run `rg -n -i "bias|representative|representativeness" CODE` and inspect the calculations at `CODE/create_figures_SSHA2025.do:310-330`; there is no population-composition comparison or downstream-estimand bias calculation supporting the conclusion.

**Suggested fix**  
Replace the bias-reduction language with the directly supported claim that coverage/linkage rates rise for several under-linked groups, or add an explicit representativeness and downstream-estimand analysis against the full census population.

### 4. The claimed random manual review has no sample size, selection code, rubric, or recorded results

`manual-review-claim-has-no-auditable-protocol` · **minor** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:305-308, CODE/compute_model_agreement_on_discordant.do:125-130`

**What the code does**  
The code mechanically assigns incomplete model output with `!(namefrst_ml!="" & namelast_ml_ditto!="")` and counts it as `nom_h`. Nothing in CODE randomly samples these records, records an image review, or classifies reviewed cases as illegibility versus segmentation failure. The paper nevertheless says a random manual review found that cases “largely” fall into those two categories.

**Why it matters**  
Without a denominator and reproducible review protocol, “largely” is not an auditable result and readers cannot distinguish systematic evidence from informal inspection. It also leaves unclear whether the statement concerns no-output cases, complete names matching neither source, or both.

**How to check**  
Run `rg -n -i "manual review|random sample|illegible|segmentation" CODE`. Verify whether a separate review dataset exists containing sampled record identifiers, reviewer classifications, and counts; none is referenced by the repository code.

**Suggested fix**  
State the sampled population and sample size, add deterministic sampling code and a short coding rubric, report category counts and overlap, and archive the anonymized classifications. Otherwise label the observation explicitly as informal and remove “random sample” and “largely.”
