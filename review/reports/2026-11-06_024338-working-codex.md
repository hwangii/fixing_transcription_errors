## Findings

### 1. The new guard still calls `abeclean` when one component contains no cleanable names

`abeclean-guard-tests-wrong-condition` · **MAJOR** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/1b_fs_divided_files.do:68-70, LINKAGE/code/01_abe_jw/reference/abeclean.ado:153-173, LINKAGE/code/01_abe_jw/reference/abeclean.ado:230-234`

**What the code does**  
The guard calls `abeclean` whenever `count if fs_namefrst!="" | fs_namelast!=""` is positive. Inside `abeclean`, however, each field is processed separately: characters outside `[a-z ]` are removed and then `split` is called on that field. Thus a file with all first names blank but at least one surname—or with raw nonempty strings that normalize entirely to empty—passes the outer guard while presenting an empty field to `split`, the same condition associated with r(2000).

**Why it matters**  
The intended fix makes the placebo runnable but may still abort the substantive FamilySearch run for a birthplace where only one name component is populated or where apparent names contain no cleanable letters. Because the pipeline iterates over all birthplace files, one such file prevents production of the baseline link counts.

**How to check**  
In Stata, create a small dataset with `fs_namefrst=""`, `fs_namelast="smith"`, and `sex=1`, then run the exact `abeclean` call from line 70. Repeat with one component containing only punctuation such as `"."`. Confirm whether either case returns r(2000). Also tabulate, by divided file, whether each component has any value remaining after the normalization at abeclean.ado:157-173.

**Suggested fix**  
Test cleanability separately for each component after applying the same normalization as `abeclean`. Generate an empty cleaned output for a component with no usable tokens while safely cleaning the other component, or update and pin the repository copy of `abeclean` so its per-field loop explicitly handles an entirely empty component.
