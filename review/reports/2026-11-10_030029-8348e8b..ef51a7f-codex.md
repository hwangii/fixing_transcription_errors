## Findings

### 1. The validation standard is selected on prior successful linkage and vital-data coverage, yet the paper presents it as independent evidence

`selected-crosswalk-presented-as-independent-validation` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `CODE/create_linked_sample_for_MLP_training.do:5-13, F:/github_repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:104-108, F:/github_repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:573-580`

**What the code does**  
The truth sample first intersects the pre-existing 1930 and 1940 FamilySearch-profile crosswalks using `merge 1:1 unique_ID ... keep(3)`, then retains only profiles with observed birth and death dates through `keep if birthyr!=. & deathyr!=. & birthmon!=. & deathmon!=. & _merge==3 ...`. The code therefore evaluates links only among people already linked successfully in both censuses and covered by the profile/vital-date data; it neither constructs nor audits those upstream crosswalk links. The paper instead calls this an “independent set of high-quality genealogical links” and uses it to distinguish genuine from spurious recovery.

**Why it matters**  
Name quality can affect inclusion in the FamilySearch crosswalk itself. If people with clear, common, or internally consistent names are more likely to enter the standard, verified counts, recall, and contradicted-link shares need not generalize to the difficult records the model targets. The direction of the reported within-standard comparisons may still be informative, but the strong independence and genuine-recovery language is not established by the supplied code.

**How to check**  
Obtain the construction documentation for `unique_ID_to_census_crosswalk1930/1940.dta` and tabulate truth-set inclusion by Ancestry–FamilySearch disagreement, name commonness, race, nativity, and baseline linkage status. Also compare old/new link outcomes separately for records with neither, one, or both census identifiers represented in the truth set.

**Suggested fix**  
Describe exactly how the two upstream profile-to-census crosswalks were created and whether census names entered those links. Recast the result as validation within a selected FamilySearch-linked subset unless independence can be demonstrated, and report truth-set coverage and selection diagnostics for the target and full samples.

### 2. The claim checker exits successfully while 37 empirical numbers in the new FamilySearch comparison remain unregistered

`unregistered-paper-results-do-not-fail-gate` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `replication/check_claims.py:263-282, replication/claims_report.md:112-155, F:/github_repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:658-695`

**What the code does**  
The checker lists uncovered numbers in `unreg`, but its exit condition is only `return 1 if bad or missing else 0`; `unreg` is not part of the failure condition. The committed report consequently records 37 uncovered numbers, including the headline 20.1%, 22.3%, and cell-level comparisons, while the command still reports success.

**Why it matters**  
The paper’s new comparison with FamilySearch names contains a dense set of headline results that can become stale without making the replication gate fail. This defeats the stated purpose of the claims registry and permits a green run even when an entire results subsection is not checked against generated outputs.

**How to check**  
Run `python replication/check_claims.py; echo $LASTEXITCODE` in PowerShell. It reports `unregistered result-like numbers in the draft: 37` but returns exit code 0. Then inspect `replication/claims_report.md` from line 112 onward.

**Suggested fix**  
Register the Section 4.3 claims and its three generated exhibits in `replication/claims.toml`, including assertions for the qualitative comparisons at paper lines 659, 686, 688, and 695. Make non-ignored uncovered result-like numbers produce a nonzero exit code.

### 3. The linkage documentation still reports obsolete truth-dependent results and the old one-sided contradiction definition

`linkage-documentation-retains-pre-rerun-results` · **minor** · claims-vs-code · confidence: **verified** (traced in source)

**What the code does**

Current code checks both census sides, and the regenerated HLINK table reports 28,786,787 and 29,301,006; the ABE/JW documentation likewise retains the pre-rerun counts and recalls.

**Why it matters**  
The paper tables are correct, but a replicator using the package documentation as expected output will conclude that a successful rerun failed or may implement the obsolete one-sided classification. The same document says the tables have used the complete file since 2026-11-09, making the inconsistency especially misleading.

**How to check**  
Run `rg -n "28,357,041|6,222,698|1940 record.*truth set" LINKAGE/DOCUMENTATION.md` and compare those rows with the four files under the paper repository’s `linkage_tables/`.

**Suggested fix**  
Regenerate or manually synchronize the results section from the current four table outputs, update the restricted denominators and match rates, and define contradiction as either census person having a different truth partner.
