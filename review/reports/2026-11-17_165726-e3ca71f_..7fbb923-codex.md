## Findings

### 1. Millions of records without measured target status are assigned to the non-target arm

`unknown-target-status-coded-nontarget` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/1c_tgt_divided_files.do:17-19, MATCHING/1c_tgt_divided_files.do:52-65, MATCHING/1c_tgt_divided_files.do:99-114, review/briefs/2026-11-17-tgt-diag.md:3-7`

**What the code does**  
The code computes `tgt = !(namefrst==namefrst_fs & namelast==namelast_fs)`, saves only `keep if tgt`, and then executes `replace tgt = 0 if _merge==1`. Consequently, a known commercial-source agreement and an ID absent from `census1940_all_labeled_data.dta` receive the same value. The committed brief reports 4,819,575 such absent divided-file records.

**Why it matters**  
Those records have not been shown to be non-targets, yet lines 111-114 force them to use Ancestry names. Their names can affect their own links and other records through candidate competition. The output is therefore target-only within the labeled universe, not necessarily replacement only on true target records across the linkage universe.

**How to check**  
Merge a divided file against a full ID list from `census1940_all_labeled_data.dta` carrying an `observed=1` marker, then run `count if _merge==1`, `count if _merge==1 & age>=10 & age<.`, and tabulate birthplace. Repeat over all files or use `tgt_fallback_diag.do`; then compare links involving these IDs and age-nearby candidate sets under Ancestry versus model-name treatment.

**Suggested fix**  
Retain a three-way status: observed target, observed non-target, and unavailable. Recover the commercial comparison for unavailable records where possible; otherwise exclude them symmetrically or report sensitivity runs assigning them first to Ancestry and then to model names. Label the resulting estimand accordingly.

### 2. The non-target subtraction does not compare all-record replacement with target-only replacement

`old-vs-new-does-not-identify-target-only-effect` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/nontarget_from_tables.py:3-13, MATCHING/nontarget_from_tables.py:53-63, review/briefs/2026-11-17-nontarget-from-tables.md:3-7, MATCHING/2_ABE_matchingV3_christian_torben.do:152-167`

**What the code does**  
The script subtracts each target-table count from the corresponding full-table count and compares the global Old and New linkage runs. It never reads `link1930_1940_mltgt1940_cleaned_noraceblock0.dta`. Moreover, ABE runs `abematch ... unique_m(2) unique_f(2)` and defines retained uniqueness using `unique_file2 == 1 & unique_match2 == 1`, so changing target names can alter non-target outcomes through candidate competition.

**Why it matters**  
The reported non-target decline cannot isolate the effect of replacing names on non-target records: both target and non-target names change between Old and New. Using it to choose between all-record and target-only replacement could support the wrong implementation.

**How to check**  
Score `link1930_1940_mltgt1940_cleaned_noraceblock0.dta` and `link1930_1940_ml1940_cleaned_noraceblock0.dta` on the identical observed non-target IDs. Merge their pairs by census ID and tabulate retained links, changed partners, and Verified/Unverifiable/Contradicted classifications.

**Suggested fix**  
Use the target-only and all-model linkage outputs for the policy comparison. Keep the All-minus-Target results only as a descriptive decomposition of the existing global Old-versus-New runs, explicitly noting that they do not identify the marginal effect of replacing non-target names.

### 3. Permitted fallback discrepancies can make the two linkage runs differ without any model-name substitution

`fallback-tolerance-confounds-linkage-contrast` · **minor** · correctness · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/1c_tgt_divided_files.do:105-114, MATCHING/1c_tgt_divided_files.do:128-135, review/briefs/2026-11-17-tgt-check-nonfatal.md:3-5`

**What the code does**  
The builder counts `name_true_cleaned_exists==0 & !(f_name==f_ans & l_name==l_ans)` but now exits only when `nbad > 0.001*nchk`, allowing the documented 436 discrepancies. For any such non-target record, lines 111-114 put `_ans_cleaned` into the target-only input while the all-record input retains the differing `_true_cleaned` fallback, despite neither version using a model transcription.

**Why it matters**  
If any discrepancies are non-targets, the runs differ for an unintended cleaning-path reason that can alter links and candidate uniqueness. The affected share is small, but the global tolerance does not establish that its link-level effect is zero.

**How to check**  
Before replacement, accumulate `count if name_true_cleaned_exists==0 & !(f_name==f_ans & l_name==l_ans) & !tgt`. After both link files exist, identify changed assignments involving those IDs or their competing candidates.

**Suggested fix**  
Reconcile the fallback-cleaning paths or require zero discrepancies specifically among non-target records. If temporarily retained, report the consequential count and demonstrate that excluding affected candidates leaves the comparison unchanged.
