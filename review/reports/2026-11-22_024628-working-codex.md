## Findings

### 1. The report says fallback initials remain unchanged even though the builder changes some of them

`fallback-initials-falsely-described-as-unchanged` · **minor** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/1e_tgtns_divided_files.do:128-134, MATCHING/score_tgt_links.do:126-131, MATCHING/score_tgt_links.do:322, review/reports/2026-11-22_022623-working-codex.md:17`

**What the code does**  
For first-name sentinels, the builder counts `sf & mi_rc!=""` and then executes `replace mi_true_cleaned = mi_rc if sf`. The scorer expressly permits `mi_tgtns!=mi_tgt` when the old initial was empty. Nevertheless, its generated prose says the fallback “leaves them unchanged” and that every such record has an empty own initial. The recorded New York/Wyoming smoke test states that 13 sentinel first names received a nonempty initial.

**Why it matters**  
The new column's `Share validated, MI` and `Links with both initials` can change because both the links and the validation variable/denominator change. The prose incorrectly presents the comparison as changing links while keeping initials fixed.

**How to check**  
Run `_tgtns_run.do` and inspect the builder's `sentinel first names whose fallback initial is non-empty` count. In the scorer, tabulate `mi_tgtns!=mi_tgt`, then compare the mltgt/mltgtns changes in `nv` and `sv` with the fixed-Ancestry `nva` and `sva` changes.

**Suggested fix**  
Remove the claims that initials are unchanged and necessarily empty. Report how many initials changed and interpret the fixed-Ancestry-MI rows as the comparison that holds the validation field constant; assert `nmi==0` only if unchanged initials are genuinely required.
