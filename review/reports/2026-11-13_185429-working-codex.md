## Findings

### 1. FamilySearch-linked profile names cannot independently validate transcription accuracy

`familysearch-profile-reference-is-endogenous` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/profile_names_build.do:3-7, MATCHING/profile_names_build.do:83-105, MATCHING/profile_names_score.do:25-31`

**What the code does**  
The code restricts the analysis to census records attached one-to-one to FamilySearch profiles and compares each transcription with the attached profile's name. It explicitly acknowledges that users may locate records through FamilySearch's index and may construct profile names from those records, but the comparison remains based on that common-source reference.

**Why it matters**  
Mechanical agreement and selective attachment can favor FamilySearch and exclude difficult or unusual names. The resulting rates measure agreement within a selected FamilySearch-linked sample, not accuracy against independent ground truth; cell-specific comparisons do not eliminate selection into the linked sample.

**How to check**  
Tabulate agreement and retention by attachment provenance, name frequency, race, nativity, and whether the profile name predates the census attachment. Independently hand-adjudicate a stratified random sample directly from census images without using any transcription to select or label records.

**Suggested fix**  
Keep the table explicitly descriptive and avoid using it as accuracy validation. Add blinded image-based adjudication for any accuracy claim, and report selection into the profile-linked sample by relevant subgroups.

### 3. The selection table reports ambiguous crosswalk rows as numbers of dropped records

`ambiguous-crosswalk-drops-count-rows-not-records` · **minor** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_build.do:91-100, MATCHING/profile_names_score.do:141-150`

**What the code does**  
The build records `n_xmh = r(N)` after `count if _mh` and `n_xmu = r(N)` after `count if _mu`; these are counts of crosswalk rows before `drop if _mh | _mu`. The output table has a `records` column and labels them as records dropped for multiple profiles or multiple records. A histid linked to two profiles contributes two rows, and rows satisfying both flags appear in both counts.

**Why it matters**  
The reported attrition numbers overstate the number of distinct affected records and overlap, so they cannot be interpreted as an additive selection flow. This can give readers the wrong magnitude of linkage ambiguity.

**How to check**  
Before dropping, run `egen tag_h = tag(histid) if _mh`, `egen tag_u = tag(unique_ID) if _mu`, then compare `count if _mh`, `count if tag_h`, `count if _mu`, `count if tag_u`, and `count if _mh & _mu`.

**Suggested fix**  
Store distinct ambiguous histid and unique_ID counts separately, report their units explicitly, and also store the union of crosswalk rows or census records removed so the flow reconciles.
