## Findings

### 1. The FamilySearch columns mix FamilySearch and Ancestry names without reporting source coverage

`familysearch-benchmark-is-selective-hybrid` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_fs_links.do:326-333, MATCHING/1b_fs_divided_files.do:83-93, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:103-120`

**What the code does**  
The upstream construction replaces each field only when `fs_namefrst_cleaned!=""` or `fs_namelast_cleaned!=""`; otherwise it retains the Ancestry field. Although `fs_frst_used` and `fs_last_used` are carried into the link files, the scorer discards them and presents columns headed `FS 1930 & 1940`, `FS 1930`, and `FS 1940`. Thus it computes linkage under a record- and field-specific FamilySearch/Ancestry fallback policy, not linkage using FamilySearch transcriptions throughout.

**Why it matters**  
FamilySearch availability is selective and plausibly correlated with name difficulty and successful source linkage. Differences from the Ancestry or ML columns therefore combine transcription differences with FamilySearch coverage and fallback selection, so they cannot isolate how a FamilySearch transcription baseline performs.

**How to check**  
For each FS link file, merge `fs_frst_used` and `fs_last_used` from the corresponding divided files and tabulate the four source patterns on each side. Recompute match rate, verification categories, and recall separately for both-fields-FS, partial-FS, and Ancestry-fallback records.

**Suggested fix**  
Retain and report the source indicators in the scoring dataset. Label the current columns explicitly as fallback policies, show their coverage composition, and add a balanced complete-case comparison restricted to records with usable FamilySearch fields on both census sides.

### 2. FamilySearch-name links are evaluated as correct using a FamilySearch-derived linkage reference

`familysearch-derived-reference-favors-familysearch-benchmark` · **MAJOR** · identification · confidence: **likely** (implied, depends on unseen data)

**Where:** `MATCHING/score_fs_links.do:34, MATCHING/score_fs_links.do:119-147, MATCHING/score_fs_links.do:185-201, CODE/create_linked_sample_for_MLP_training.do:5-17`

**What the code does**  
The script names `mlp_training1930_1940.dta` as `true_links`, classifies an exact pair as `ver`, and outputs that category as `Verified Correct`. The reference file is constructed from profile-to-census crosswalks and profile vital dates, while the new comparison columns use FamilySearch census names. It therefore treats agreement with a FamilySearch-derived crosswalk as correctness when evaluating a FamilySearch-based linkage policy.

**Why it matters**  
If census records were attached to FamilySearch profiles using FamilySearch's own index or related hints, the FamilySearch-name columns have a mechanically favored validation target. Higher verified counts or recall would then not establish that FamilySearch transcriptions are more accurate than Ancestry or ML; they would partly measure common-source dependence.

**How to check**  
Document how the MLP crosswalk attached 1930 and 1940 census records to profiles. Then repeat the comparison on independently hand-adjudicated links, or at minimum on records where the ML and FamilySearch census names disagree and on reference links anchored by non-census vital records.

**Suggested fix**  
Describe the reference as a comparison linkage rather than ground truth unless independence is established. Add an independent validation or sensitivity sample and qualify `Verified Correct` and `Recall` accordingly.

### 3. The table's added and removed rows exclude every link whose 1940 partner changes

`partner-switches-omitted-from-added-removed-rows` · **MAJOR** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_fs_links.do:258-264, MATCHING/score_fs_links.do:286-300, MATCHING/score_fs_links.do:341-346`

**What the code does**  
When a 1930 record appears in both link sets with different 1940 partners, the code assigns `status = "changed"`. It computes truth categories for these records, but the reported scalars count only `status == "net_added"` and `status == "net_removed"`; the output nevertheless labels them `Added vs. Ancestry` and `Removed vs. Ancestry`. At the pair level, each changed record contributes one added pair and one removed pair, neither of which appears in those rows.

**Why it matters**  
The generated table understates pair churn and suppresses whether FamilySearch replaces a correct Ancestry partner with an incorrect one or vice versa. Any claim based on these rows about how many links FamilySearch adds, removes, verifies, or contradicts is incomplete.

**How to check**  
Run `tab status` and cross-tabulate `old_cat` by `new_cat` for `status=="changed"`. Independently merge the Ancestry and comparison files on `histid1930 histid1940`; the pair-set additions and removals should exceed the displayed net-added/net-removed totals by the number of changed partners.

**Suggested fix**  
Either relabel the current rows `Net newly linked records` and `Net no-longer-linked records` and add a complete old-category-by-new-category panel for switched partners, or calculate added and removed pairs directly from pair-set differences.

### 4. No replication master or manifest runs the new scorer or preflights its inputs

`familysearch-scorer-omitted-from-replication-runner` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_fs_links.do:30-41, replication/run_machineA.do:39-49, replication/run_machineA.do:80-90, replication/run_machineB.do:44-68`

**What the code does**  
The new script directly reads three FamilySearch link files, two divided-file directories, a congruence file, and the MLP reference, then writes `MATCHING/results/fs_linkage_abe.tex`. Neither machine master invokes `score_fs_links.do`; their preflight input lists omit the FamilySearch link files and divided-file directories. Repository searches for `score_fs_links` and `fs_linkage_abe` under the replication runners return no references.

**Why it matters**  
Running the documented replication workflow cannot produce or validate this new table. A missing, stale, or partially generated FamilySearch input remains outside the package's preflight and checksum guarantees, so the result is not reproducible from the advertised entry points.

**How to check**  
Run `rg -n "score_fs_links|fs_linkage_abe|link1930_1940_fs" replication` and compare the result with the input declarations in both machine masters. Then run the documented masters and confirm that `MATCHING/results/fs_linkage_abe.tex` is not created.

**Suggested fix**  
Add a documented machine-A stage that preflights and hashes every required FamilySearch input, runs the scorer, and registers its output and claims. If construction of the link files remains outside the frozen analysis tier, document that prerequisite and its provenance explicitly.
