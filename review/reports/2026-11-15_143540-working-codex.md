### 1. The new denominator artifact is manually transferred and absent from the current input manifest

`new-sample-outside-replication-pipeline` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `LINKAGE/code/prep/build_linkage_sample1940.do:16-18, LINKAGE/code/prep/build_linkage_sample1940.do:27, LINKAGE/code/prep/_run_build_linkage_sample1940.do:1-2, replication/run_machineB.do:59-65, replication/hash_inputs_machineB.py:35, replication/input_manifest_machineB.md:4-21`

**What the code does**  
The builder saves `linkage_sample1940.dta` to machine A's `$REP_SNU/.../DATA/INTERMEDIATE` and instructs the author to copy it to machine B's `$D_FLAGS`; the only runner is an untracked, hardcoded wrapper. Machine B now preflights that copied file, and the hashing script expects 15 inputs, but `input_manifest_machineB.md` still records 17 inputs, includes the three superseded files, and contains no hash for `linkage_sample1940.dta`.

**Why it matters**  
The current documented `python replication/hash_inputs_machineB.py --check` must report the new sample as changed or new, so the regenerated Tables 5–8 cannot pass the repository's frozen-input integrity check. An external replicator also cannot produce the defining denominator artifact through either master pipeline without discovering and performing an undocumented cross-machine transfer.

**How to check**  
Run `python -c "import replication.hash_inputs_machineB as h; print('\n'.join(h.input_list()))"` and compare its 15 paths with `replication/input_manifest_machineB.md`; then run `rg -n "build_linkage_sample1940|linkage_sample1940" replication LINKAGE/code` to confirm that no tracked master invokes the builder or performs the transfer.

**Suggested fix**  
Add the builder to the machine-A master, script a checksummed transfer into machine B's expected path, and regenerate `replication/input_manifest_machineB.md` on machine B so it contains the 15 active inputs and the new file's SHA-256 before accepting regenerated tables.

### 2. The Old/New MI comparison changes the validator as well as the linked pairs

`moving-middle-initial-validator` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `LINKAGE/code/01_abe_jw/linkage_analysis.do:242-254, LINKAGE/code/01_abe_jw/linkage_analysis.do:486-512, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:374-386, LINKAGE/code/02_hlink/linkage_analysis_newlinks.do:551-578`

**What the code does**  
For Old links, `miv` is `mi_anc`; for New links it is `mi_ml`. The code then computes `count if mi1930 == mi1940` and presents the resulting rates side by side as `MI Match Rate (%)` in a panel titled `Coverage and Link Quality`. Thus both the candidate links and the 1940 initial against which they are evaluated change between columns.

**Why it matters**  
A higher New rate can result from the model re-transcribing the 1940 middle initial differently even when the linked pair is unchanged. The revised captions disclose the own-initial convention, but the row still cannot be interpreted as an isolated improvement in link quality; a referee will require a fixed-validator comparison for that claim.

**How to check**  
Run `replication/diagnostics/validation_fixed_initials.do`, then score the ABE, JW, and HLINK Old/New pairs twice—once using `mi_anc` for both versions and once using `mi_ml` for both—and compare those changes with the reported own-initial changes.

**Suggested fix**  
Report a fixed-validator MI rate as the link-quality comparison, preferably alongside the disclosed own-transcription rate. At minimum, rename the existing row and panel so they do not characterize its Old/New difference as independent linkage validation.
