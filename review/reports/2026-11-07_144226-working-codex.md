## Findings

### 1. The scorer fails when it reaches either one-year FamilySearch link file

`one-sided-fs-files-request-nonexistent-indicators` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:83-90, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:68-71, MATCHING/3_append_and_clean_all_links_christian_torbenV2.do:105-120`

**What the code does**  
For every combination beginning with `fs`, line 84 sets `fsv` to `fs_used1930 fs_used1940`, and line 85 requests both variables through `keepusing(...)`. Upstream, however, `gen byte fs_used`y' = ...` runs only when that year's `type` equals `fstype`; therefore the FS-1930-only file has no `fs_used1940`, and the FS-1940-only file has no `fs_used1930`. The scorer should request only the indicator present in each file and assign zero to the unused year.

**Why it matters**  
Stata stops with a variable-not-found error on the first one-year FamilySearch file, before `fs_avg_performance.tex` is written. Consequently none of the intended five-column comparison can be generated by this script.

**How to check**  
In Stata, run `describe fs_used1930 fs_used1940 using "<links>/link1930_1940_fs1930_cleaned_noraceblock0.dta"` and repeat for `link1930_1940_fs1940_cleaned_noraceblock0.dta`; each should show that one requested variable is absent. Then run the do-file and confirm it stops at line 85.

**Suggested fix**  
Define `fsv` by combination: both indicators for `fs12`, only `fs_used1930` for `fs30`, and only `fs_used1940` for `fs40`. In the year loop, explicitly generate zero for the year that does not use FamilySearch.

### 2. No documented master workflow runs or preflights the new scorer

`fs-performance-table-outside-master-workflow` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/fs_avg_performance.do:24-35, MATCHING/fs_avg_performance.do:153-189, MATCHING/_matching_master_dofile.do:85-101, replication/run_machineA.do:39-67, replication/run_machineA.do:80-105`

**What the code does**  
The script alone writes `MATCHING/results/fs_avg_performance.tex`, but the matching master exits immediately after constructing one requested FamilySearch link configuration, while `run_machineA.do` invokes only its fixed CODE and diagnostic lists. Its preflight includes the Ancestry and ML link files but not the three `link1930_1940_fs*.dta` inputs. Standalone bootstrapping also hardcodes `D:/repos/fixing_transcription_errors/replication/config.do`.

**Why it matters**  
Running the documented replication entry point will never regenerate this table, and missing or stale FamilySearch link inputs are not detected in preflight. A submitted FamilySearch comparison could therefore be manual or stale rather than reproducible from the archive.

**How to check**  
Run `rg -n "fs_avg_performance" -g "*.do" -g "*.ps1" -g "*.py" --glob "!review/reports/**" .`; the only matches are inside the scorer itself. Compare its inputs at lines 31-35 with the preflight list in `replication/run_machineA.do:39-53`.

**Suggested fix**  
Add a documented top-level FamilySearch workflow that builds all three link variants, preflights every input, runs `MATCHING/fs_avg_performance.do`, and registers its TeX output. Bootstrap configuration through that master or a portable repository-root mechanism rather than a literal machine-A path.
