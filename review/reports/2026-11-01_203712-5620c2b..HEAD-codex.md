## Findings

### 1. The paper reports a 28% match-quality gain that falls to 11.5–16.0% when the validator is held fixed

`moving-validator-overstates-quality-gain` · **BLOCKER** · claims-vs-code · confidence: **verified** (traced in source)

**Where:** `CODE/create_figures_SSHA2025.do:70-83, replication/diagnostics/validation_fixed_initials.do:55-80, replication/results/validation_fixed_initials.tex:13-15, replication/results/validation_fixed_initials.tex:23-25, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:68, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:97-98, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:547-549`

**What the code does**  
The paper-producing code constructs `validated_before=mi1930==mi1940` after importing both initials from the old-name link file, then constructs `validated_after=mi1930==mi1940` after importing them again from the new-name link file. Thus the 1940 validating value changes with the treatment. The new diagnostic instead computes `vb_src = mi1930_old==mi_src` and `va_src = mi1930_new==mi_src` using one fixed 1940 initial. Its committed results are 64.3% to 74.5%, or 16.0% relative growth, with Ancestry and 72.9% to 81.3%, or 11.5%, with FamilySearch—not the draft’s 65% to 84%, or 28%.

**Why it matters**  
The abstract and main results report the 28% figure as improved match quality and infer that true matches rather than spurious matches were recovered. The new diagnostic establishes that much of that reported improvement came from changing the validator itself, so the headline result is numerically wrong under either fixed-source specification.

**How to check**  
Run `do replication/diagnostics/validation_fixed_initials.do`, then compare `valGainAncTarget` and `valGainFsTarget` in `replication/results/validation_fixed_initials.tex` with `shareValTargetBefore`, `shareValTargetAfter`, and `valGainTarget` in `replication/results/create_figures_SSHA2025.tex`.

**Suggested fix**  
Choose and justify a validator held fixed across old and new linkages, regenerate the main table from that specification, and replace every 28% claim in the abstract, introduction, and results. Report the Ancestry-versus-FamilySearch sensitivity unless one source can be defended as independently preferable.

### 2. The claim checker still certifies the obsolete 28% result and the master never regenerates the corrective diagnostic

`claim-checker-certifies-obsolete-validator` · **MAJOR** · replication · confidence: **verified** (traced in source)

**What the code does**

It does not reference the new `valBeforeAncTarget`/`valAfterAncTarget` or FamilySearch equivalents, so `claims_report.md` reports the stale 65/84/28 claim as `MATCH`. Moreover, the Machine A `local scripts` list omits `validation_fixed_initials`, leaving its committed output outside the reproducible master run.

**Why it matters**  
The package’s automated safeguard now gives false assurance for the paper’s central disputed result. A normal replication run can finish with a successful claim check while neither regenerating nor considering the diagnostic that contradicts that claim.

**How to check**  
Run `rg -n "results-validated|validation_fixed_initials" replication/claims.toml replication/run_machineA.do replication/claims_report.md`; the claim is mapped only to the original outputs, and the diagnostic is absent from the master script list.

**Suggested fix**  
Add the fixed-initial diagnostic to the Machine A master and preflight inputs, remap the validation claims in `claims.toml` to the chosen fixed-source macros, and make the alternative-source result an explicit sensitivity check. The claim check should fail until the draft’s 28% statements are updated.

### 3. Middle-initial validation observes only 20.3% of added target links, but the paper generalizes its quality inference to all added links

`validation-covers-selected-fifth-of-added-links` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `replication/diagnostics/validation_by_link_status.do:61-74, replication/results/validation_by_link_status.tex:53-58, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:542, D:/repos/6638fa0fd89fbec05130caeb/DHTS-2026-10-12.tex:547-549`

**What the code does**  
The diagnostic computes validation using `summarize validated_after`, which excludes missing initials, and now correctly writes both that `r(N)` and `100*nmi/nlinks`. The committed output shows only 396,760 of 1,953,052 added target links have usable initials, or 20.3%; for dropped links it is 82,178 of 434,677, or 18.9%. The paper notes that validation is computed when initials are available but then uses the resulting rate to conclude generally that the new links are true rather than spurious.

**Why it matters**  
Initial availability is potentially related to name structure, transcription difficulty, and population characteristics. Agreement within the observable fifth does not identify the quality of the other roughly 80% of added links, so a referee will require either evidence that missingness is benign or a narrower conclusion.

**How to check**  
Tabulate `!missing(validated_after)` for added links and `!missing(validated_before)` for dropped links by race, nativity, legibility quartile, name frequency, and linkage outcome. Compare those distributions with the full added/dropped samples and with coverage by the genealogical reference set.

**Suggested fix**  
Report the validation numerator and denominator beside every rate, disclose the 20.3% coverage in the main text or table note, test selection into observable initials, and restrict the inference to links with initials unless the separate genealogical validation supports the remainder.
