## Findings

### 1. The replication gate omits every truth-based statistic that the report outputs

`truth-rows-bypass-replication-gate` · **MAJOR** · correctness · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_tgt_links.do:118-125, MATCHING/score_tgt_links.do:164-180, MATCHING/score_tgt_links.do:203-227, MATCHING/score_tgt_links.do:256-270`

**What the code does**  
The script merely displays the truth count with `display "truth pairs: " _N " (expected 36,690,338)"`. Its stopping gate checks only `N_*`, `nv_*`, `rate_*`, and `sv_*`; it never checks `ver_*`, `unv_*`, `con_*`, `FN_*`, or `recall_*`, although all of those are subsequently written to the report. It was evidently intended to establish that the Old and New columns reproduce the reference linkage analysis before scoring the new columns.

**Why it matters**  
A wrong or incomplete truth file—or a divergence in the classification logic—can change every Verified, Unverifiable, Contradicted, contradiction-share, and recall result while the script prints `CHECK PASSED` and writes a plausible report. This is particularly material because the repository documents multiple historical copies of this multi-gigabyte benchmark.

**How to check**  
In Stata, load `$REP_F/fixing_transcription_errors/DATA/INTERMEDIATE/mlp_training1930_1940.dta`, run `isid histid1930`, `isid histid1940`, and `assert _N==36690338`; then compare the scorer’s ans/true V/U/C and recall values with the ABE Old/New rows generated by `LINKAGE/code/01_abe_jw/linkage_analysis.do`.

**Suggested fix**  
Make the expected truth count and one-to-one uniqueness hard stops, and add expected ans/true V/U/C and recall values to the existing `bad` gate. Do not open the Markdown output unless all truth-based and non-truth-based reference rows reproduce.

### 2. Contradiction shares compare different method-selected subsets of a selected genealogical benchmark

`selected-reference-confounds-contradiction-share` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_tgt_links.do:164-180, MATCHING/score_tgt_links.do:256-270, CODE/create_linked_sample_for_MLP_training.do:5-13`

**What the code does**  
Each method’s proposed links are classified against `mlp_training1930_1940.dta`, and the reported ratio is `con_*/(ver_*+con_*)`, excluding unverifiable links. The benchmark itself is created by inner-merging records attached to the same FamilySearch profile in both censuses and retaining profiles with complete, ordered birth and death dates. Because each transcription version proposes different links, each column’s `ver+con` denominator is a different selected population.

**Why it matters**  
Differences in the reported contradiction share can reflect which people and proposed partners are covered by the FamilySearch-derived reference, rather than differences in link accuracy. The target/non-target comparison does not remove this selection, so these values cannot identify population error rates or clean accuracy improvements without additional evidence.

**How to check**  
For every sample and link version, tabulate truth coverage and `unv/L`, then compare coverage by target status, name frequency, race, nativity, and whether the model agrees with FamilySearch. Recompute V/C comparisons on a fixed common set of 1940 IDs covered by the reference across all four versions.

**Suggested fix**  
Label the statistic explicitly as contradiction among reference-covered proposed links, report coverage beside it, add a common-support comparison, and qualify extrapolation beyond the FamilySearch-attached sample. Use an independently hand-adjudicated sample for claims about population accuracy.

### 3. The new target-only result is absent from the replication master and input preflight

`target-scorer-outside-replication-master` · **MAJOR** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/score_tgt_links.do:31-42, MATCHING/_tgt_only_run.do:46-52, replication/run_machineA.do:39-68, replication/run_machineA.do:96-149`

**What the code does**  
The scorer directly consumes the `ml1940` and `mltgt1940` link files plus divided-file directories, but `replication/run_machineA.do` neither preflights those inputs nor invokes `score_tgt_links.do`. The target-only link build is a separate manual run, and the standard replication workflow therefore never produces `MATCHING/results/tgt_linkage_abe.md`.

**Why it matters**  
A replicator can complete the documented master successfully without recreating or even checking this result. The result consequently depends on unmanifested external files and a manual machine-specific sequence, allowing stale or differently generated links to survive unnoticed.

**How to check**  
Run `rg -n "score_tgt_links|mltgt1940|ml1940|tgt_linkage_abe" replication`; there are no references. Also run `replication/Run-MachineA.ps1` in an environment with the existing frozen inputs and confirm that it neither checks the two new link files nor creates the Markdown result.

**Suggested fix**  
If this result will enter the paper or slides, add its frozen inputs to the preflight and input manifest, invoke the scorer from the appropriate master, document whether `_tgt_only_run.do` is build-tier or required analysis-tier code, and track/register the generated exhibit. Otherwise mark it explicitly as a non-replicated diagnostic and do not cite it as a paper result.
