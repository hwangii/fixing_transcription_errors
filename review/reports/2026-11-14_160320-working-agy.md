## Findings

### 1. Conditioning on a death month does not establish that profile names are independent of the attached census index

`death-month-does-not-establish-name-independence` · **MAJOR** · identification · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:148-155, MATCHING/profile_names_score.do:278-286`

**What the code does**  
The code constructs has_dmonth using a regex check on deathdate (lines 148-155) and scores agreement on this subgroup (lines 278-286), claiming in comments that 'a profile with a death month was built from sources beyond the census, and its name is less likely to be a copy of the attached census index'. In fact, the code only observes that an external death fact was attached to the profile; it does not observe or condition on the provenance of fullname, which is often populated directly from FamilySearch's 1940 census index when the record is attached.

**Why it matters**  
FamilySearch profiles routinely combine a name initially populated from FamilySearch's 1940 census index with later-attached vital records (e.g., SSDI). Restricting to profiles with a death month does not remove FamilySearch's mechanical advantage or validate claims of transcription accuracy. Presenting this subgroup as an independence robustness check risks rejection by referees familiar with FamilySearch linkage dynamics.

**How to check**  
Audit a sample of profiles where has_dmonth==1 in FamilySearch Family Tree to inspect the change log for fullname. Check what fraction had their primary name established by attaching the 1940 census index vs an independent vital record.

**Suggested fix**  
Do not describe the death-month subgroup as establishing independence from the census index or mitigating common-source bias. Frame it strictly as a descriptive subgroup analysis (e.g., profiles with post-1940 vital records attached), or validate name provenance directly using external, hand-verified ground truth.

### 3. Split-name cache checks file modification time but ignores changes to normalization and parsing code

`persistent-name-cache-invalidated-only-by-input-timestamp` · **minor** · replication · confidence: **verified** (traced in source)

**Where:** `MATCHING/profile_names_score.do:113-137`

**What the code does**  
Lines 125-136 reuse cached refs_*.dta files whenever t_ref > t_pn (i.e. the cache file header date is newer than profile_names.dta). The cache validity check does not verify the version, checksum, or code of pnorm, xsplit, or extrname. Instead, a comment at lines 114-115 instructs the user to manually delete refs_*.dta whenever normalization changes.

**Why it matters**  
If a researcher modifies name normalization rules in pnorm (e.g., adding/modifying suffixes, punctuation, or nickname handling), subsequent runs will silently reuse stale split names from disk without throwing an error or warning, causing silent divergence between code and results.

**How to check**  
Inspect lines 128-133 of MATCHING/profile_names_score.do: `local t_ref = clock(\`"c(filedate)"\', "DMYhm")` and `local t_pn = clock(\`"pn_date"\', "DMYhm")`. Notice that no check on script hash or normalization version is performed.

**Suggested fix**  
Include a code version or checksum token in the cache metadata (or embed a version string in the cache filename), and invalidate the cache if the token does not match the current script version.
